17.5. Reparación de sistemas de archivos dañados en el momento del arranque 17.5. Reparación de sistemas de archivos dañados en el momento del arranque Objetivos Reparar sistemas de archivos que están mal configurados o dañados y que hacen que el proceso de arranque se detenga prematuramente. Problemas con el sistema de archivos Durante el proceso de arranque, la unidad systemd monta los sistemas de archivos persistentes que están definidos en el archivo /etc/fstab. Los errores en el archivo /etc/fstab o sistemas de archivos dañados pueden impedir que un sistema complete el proceso de inicio. En algunos escenarios de falla, el sistema sale del proceso de inicio y abre un shell de emergencia que requiere la contraseña del usuario root. La siguiente lista describe algunos problemas comunes de montaje del sistema de archivos al analizar el archivo /etc/fstab durante el proceso.

boot process:

Sistema de archivos dañado La unidad systemd intenta reparar el sistema de archivos. Si el problema no se puede reparar automáticamente, el sistema abre un shell de emergencia. Dispositivo de almacenamiento, UUID de dispositivo o punto de montaje inexistente. La unidad systemd agota el tiempo de espera a que el dispositivo de almacenamiento esté disponible. Si el dispositivo no responde, el sistema abre un caparazón de emergencia. Comprobación y reparación de daños en el sistema de archivos Red Hat Enterprise Linux 10 proporciona herramientas para comprobar y reparar problemas del sistema de archivos. En el caso de problemas menores que se detectan durante el arranque, estas utilidades intentan reparar el sistema de archivos automáticamente. Para los sistemas de archivos de diario, como XFS y ext4, puede que solo sea necesario reproducir el diario, lo que suele ser una operación rápida. En el caso de problemas de corrupción más graves del sistema de archivos, un administrador del sistema puede utilizar las herramientas para comprobar y reparar los sistemas de archivos manualmente. La herramienta que ayuda a mantener los sistemas de archivos en buen estado durante el arranque se conoce genéricamente como herramienta de verificación del sistema de archivos o comando fsck. Sin embargo, la herramienta que repara el sistema de archivos XFS no sigue la misma convención de nomenclatura. Aunque hay un archivo binario fsck.xfs en el sistema, su único propósito es satisfacer los requisitos de arranque y sale inmediatamente con un código de salida de 0. El comando xfs_repair puede verificar y reparar problemas con los sistemas de archivos XFS que una reparación automática no soluciona.

root@host:~# xfs_repair block-device

Para realizar operaciones de verificación y reparación en sistemas de archivos ext4, use el comando fsck.ext4, que es un enlace físico al comando e2fsck que también cubre los sistemas de archivos ext3 y ext2 heredados. Utilice la opción -p para reparar automáticamente problemas menores sin intervención del usuario.

root@host:~# fsck.ext4 -p block-device

Advertencia El procedimiento adecuado para reparar un sistema de archivos es montar y desmontar el sistema de archivos para que reproduzca los archivos de registro para evitar datos corruptos o residuales. Además, el sistema de archivos debe desmontarse antes de ejecutar los comandos xfs_repair o e2fsck para evitar una posible pérdida o corrupción de datos. Reparación de problemas del sistema de archivos durante el arranque Para acceder a un sistema que no puede completar el arranque debido a problemas del sistema de archivos, la arquitectura de la unidad systemd proporciona un destino de arranque de emergencia, que abre un shell de emergencia que requiere la contraseña de root para acceder. El siguiente ejemplo muestra el resultado del proceso de arranque cuando el sistema encuentra un problema en el sistema de archivos y cambia al modo

emergency target:

[DEPEND] Error de dependencia para /mnt/mountfolder [DEPEND] Error de dependencia para sistemas de archivos locales. Proporcione la contraseña de root para mantenimiento (o presione Control-D para continuar): La unidad systemd no pudo montar el dispositivo /dev/sda2 y se agotó el tiempo de espera. Debido a que el dispositivo no está disponible, el sistema abre un shell de emergencia para acceso de mantenimiento. Para reparar problemas del sistema de archivos cuando su sistema abre un shell de emergencia, primero ubique el sistema de archivos erróneo y luego

find and repair the fault. Now reload the systemd unit configuration to retry the automatic mounting.

Utilice el comando mount para encontrar qué sistemas de archivos están montados actualmente en la unidad systemd.

root@host:~# mount

...salida omitida... /dev/sda1 en / escriba xfs (ro,relatime,seclabel,attr2,inode64,noquota) ...salida omitida... Dependiendo de en qué etapa del proceso de arranque se encuentre el sistema cuando aparece el problema, es posible que el sistema de archivos raíz aún esté montado en modo de solo lectura. Si el sistema de archivos raíz está montado con la opción ro (solo lectura), entonces no podrá editar el archivo /etc/fstab. Vuelva a montar temporalmente el sistema de archivos raíz con la opción rw (lectura/escritura) para editar el archivo /etc/fstab. La opción de remontar cambia los parámetros de montaje sin desmontar el sistema de archivos.

root@host:~# mount -o remount,rw /

Intente montar todos los sistemas de archivos enumerados en el archivo /etc/fstab utilizando la opción --all del comando de montaje. Esta opción procesa todas las entradas del sistema de archivos, pero omite aquellos sistemas de archivos que ya están montados. El comando muestra los errores que ocurren al montar un sistema de archivos.





17.5. Reparación de sistemas de archivos dañados en el momento del arranque

root@host:~# mount --all
mount: /mnt/mountfolder: mount point does not exist.

En este escenario, donde el directorio /mnt/mountfolder no existe, cree el directorio /mnt/mountfolder antes de volver a intentar el montaje. Pueden aparecer otros mensajes de error, incluidos errores tipográficos en las entradas o nombres de dispositivos o UUID incorrectos. Después de corregir todos los problemas en el archivo /etc/fstab, informe al demonio systemd que registre el nuevo archivo /etc/fstab usando el comando systemctl daemon-reload.

root@host:~# systemctl daemon-reload

Luego, vuelva a intentar montar todas las entradas.

root@host:~# mount --all

La unidad systemd procesa el archivo /etc/fstab transformando cada entrada en un tipo de montaje y luego iniciando la unidad como un servicio. El comando systemctl daemon-reload solicita a la unidad systemd que reconstruya y recargue todas las configuraciones de la unidad. Si la opción --all del comando de montaje tiene éxito sin más errores, entonces la prueba final es verificar que los sistemas de archivos se monten correctamente durante el inicio del sistema. Reinicie el sistema y espere a que se complete el inicio.

root@host:~# systemctl reboot

Para una prueba rápida del archivo /etc/fstab, utilice la opción de entrada de montaje nofail. El uso de la opción nofail en una entrada /etc/fstab permite que el sistema arranque incluso si el montaje del sistema de archivos no tiene éxito. Esta opción no debe usarse con sistemas de archivos de producción que siempre deben montarse. Con la opción nofail, una aplicación podría iniciarse cuando faltan datos del sistema de archivos, con posibles consecuencias graves.

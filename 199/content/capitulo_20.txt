# Capítulo 17. Control y solución de problemas del proceso de arranque

## 17.1. Administrar el cargador de arranque y la línea de comandos del kernel

17.1. Administrar el cargador de arranque y la línea de comandos del kernel 17.1. Administrar el cargador de arranque y la línea de comandos del kernel Objetivos Describir cómo el cargador de arranque selecciona y carga el sistema operativo, reinstala el cargador de arranque y modifica la configuración del cargador de arranque y los argumentos de la línea de comandos del kernel. El cargador de arranque Los sistemas informáticos modernos son combinaciones complejas de hardware y software. Pasar de un estado indefinido y apagado a un sistema en ejecución con un mensaje de inicio de sesión requiere que muchas piezas de hardware y software funcionen juntas. Cuando se enciende una computadora, carga un sistema de arranque de firmware desde un chip ROM en la placa base. En las máquinas x86 modernas, este sistema de arranque de firmware suele ser una interfaz de firmware extensible unificada (UEFI) o un sistema básico de entrada/salida (BIOS). La BIOS era más común en las máquinas fabricadas antes de 2020 y UEFI es el sistema más común presente en las placas base actuales. El trabajo del sistema de arranque del firmware es cargar un cargador de arranque desde un disco y pasar el control del proceso de arranque al cargador de arranque. Los cargadores de arranque son programas diseñados para interactuar con el sistema de arranque del firmware, configurar el sistema para el arranque y luego iniciar el kernel para continuar con la inicialización del sistema. El cargador de arranque predeterminado para Red Hat Enterprise Linux 10 es el GRand Unified Bootloader versión 2 (GRUB2). GRUB2 con UEFI En un sistema UEFI, el firmware de arranque lee la configuración de la RAM no volátil (NVRAM) para determinar qué disco y aplicación de interfaz de firmware extensible (EFI) cargar. El disco normalmente contiene una partición del sistema EFI, que generalmente está montada en el directorio /boot/efi. GRUB2 genera archivos que el sistema UEFI puede cargar. Una vez cargada la aplicación EFI del cargador de arranque GRUB2, el sistema pasa a la siguiente etapa de arranque. GRUB2 con BIOS En un sistema BIOS, el firmware de arranque lee un sector de arranque especialmente formateado en un disco para la imagen del cargador de arranque boot.img. Esta imagen del cargador de arranque carga la imagen core.img desde el espacio MBR sin particiones antes de la primera partición. La imagen core.img carga módulos adicionales que pueden inicializar sistemas de archivos y el sistema pasa a la siguiente etapa de arranque. GRUB2 genera e instala estas imágenes en el espacio MBR del disco. Etapas de inicio adicionales Después de que GRUB2 haya inicializado y cargado completamente los discos, presenta un menú de inicio al usuario.

El valor del índice es el número de entrada para la lista del menú de inicio, comenzando en 0. El valor del kernel es la ruta al kernel de Linux que carga GRUB2. El valor initrd es la ruta a la imagen inicial del sistema de archivos RAM, dentro de la cual arrancan las primeras etapas de Linux. El valor del título es el nombre que se muestra para la entrada de inicio en el menú de inicio de GRUB2. El valor de identificación es un identificador único para esta entrada de inicio.

Exploración del proceso de inicio y selección de un destino de inicio Objetivos Describir cómo se inicia un sistema Red Hat Enterprise Linux, cambiar el destino de inicio predeterminado e iniciar manualmente el sistema en un destino distinto al predeterminado. Inicialización del sistema en Red Hat Enterprise Linux 10 Una vez que se enciende el sistema y se inicia el cargador de arranque, comienza el proceso de inicialización del sistema. La siguiente lista ofrece una descripción general de alto nivel del proceso de inicialización del sistema en Red Hat Enterprise Linux 10. El cargador de arranque carga el kernel y la imagen initramfs desde el disco y los coloca en la memoria. La imagen initramfs es un archivo con los módulos del kernel para todo el hardware requerido en el arranque, scripts de inicialización y más. En RHEL 10, la imagen initramfs contiene un sistema de archivos raíz de arranque con un kernel en ejecución y una unidad systemd. Puede utilizar el comando lsinitrd para inspeccionar la imagen initramfs y extraer su contenido. El cargador de arranque pasa el control al kernel, junto con las opciones especificadas en la línea de comando del kernel y la ubicación de la imagen initramfs en la memoria. El kernel inicializa todo el hardware para el cual puede encontrar un controlador en la imagen initramfs y luego ejecuta el

/sbin/init script from the initramfs image as PID 1. You can override this script by using the init= kernel

parámetro. En RHEL 10, el script /sbin/init es un enlace simbólico a la unidad systemd. La unidad systemd de la imagen initramfs ejecuta todas las unidades para el objetivo initrd.target. Esta unidad incluye el montaje del sistema de archivos raíz en el directorio /sysroot, que aparece en el archivo /etc/fstab del disco. El kernel cambia (pivota) el sistema de archivos raíz desde la imagen initramfs al sistema de archivos raíz en el directorio /sysroot. Luego, la unidad systemd se vuelve a ejecutar utilizando la copia instalada de la unidad systemd en el disco. Entonces, la unidad systemd tiene el control total del proceso de arranque. La unidad systemd busca un destino predeterminado, que está configurado en el sistema o se pasa desde la línea de comandos del kernel. Luego, la unidad systemd inicia (y detiene) las unidades para cumplir con la configuración para ese objetivo y resuelve automáticamente las dependencias entre unidades. Estos objetivos normalmente inician un inicio de sesión basado en texto o una pantalla de inicio de sesión gráfica, completando así el proceso de inicio. Selección de un objetivo systemd Un objetivo systemd es un conjunto de unidades systemd que el sistema debe comenzar para alcanzar el estado deseado. 17.3. Exploración del proceso de inicio y selección de un destino de inicio El destino de emergencia monta el sistema de archivos raíz en modo de solo lectura. En este punto, el usuario root no puede cambiar el archivo /etc/fstab hasta que la unidad se vuelva a montar en modo lectura/escritura usando el comando mount -o remount,rw /. Por el contrario, el objetivo de rescate espera a que se complete la unidad sysinit.target, de modo que se inicialice una mayor parte del sistema, como el servicio de registro o el montaje de sistemas de archivos con acceso de lectura/escritura. Los administradores pueden utilizar estos shells para solucionar problemas que impiden que el sistema se inicie como se esperaba, por ejemplo, un bucle de dependencia entre servicios o una entrada incorrecta en el archivo /etc/fstab. Después de salir de estos shells, el sistema continúa con el proceso de inicio estándar. Seleccione un destino diferente en el momento del arranque Para seleccionar un destino diferente en el momento del arranque, agregue la opción systemd.unit=target.target a la línea de comando del kernel desde el cargador de arranque. Por ejemplo, para iniciar el sistema en un shell de rescate donde puede cambiar la configuración del sistema casi sin

services running, append the following option to the kernel command line from the boot loader:
systemd.unit=rescue.target

Este cambio de configuración afecta solo a un inicio y es una herramienta útil para solucionar problemas del proceso de inicio. Para utilizar este método para seleccionar un destino diferente, siga estos pasos: Apagar y reiniciar Para apagar o reiniciar un sistema en ejecución desde la línea de comandos, puede utilizar el comando systemctl. El comando systemctl poweroff detiene todos los servicios en ejecución, desmonta todos los sistemas de archivos (o los vuelve a montar como de solo lectura cuando no se pueden desmontar) y luego apaga el sistema. El comando systemctl reboot detiene todos los servicios en ejecución, desmonta todos los sistemas de archivos y luego reinicia el sistema. También puede utilizar la versión más corta de estos comandos, poweroff y reboot, que son enlaces simbólicos al

systemctl unit equivalents.

Nota Los comandos systemctl halt y halt también están disponibles para detener el sistema. A diferencia del apagado

command, these commands do not power off the system; they bring down a system to a point where it is safe

para apagarlo manualmente. Inicie o reinicie el sistema. 1. En el menú de GRUB2, interrumpa la cuenta regresiva presionando cualquier tecla (excepto Enter, que inicia un inicio normal). 2. 17.5. Reparación de sistemas de archivos dañados en el momento del arranque 17.5. Reparación de sistemas de archivos dañados en el momento del arranque Objetivos Reparar sistemas de archivos que están mal configurados o dañados y que hacen que el proceso de arranque se detenga prematuramente. Problemas con el sistema de archivos Durante el proceso de arranque, la unidad systemd monta los sistemas de archivos persistentes que están definidos en el archivo /etc/fstab. Los errores en el archivo /etc/fstab o sistemas de archivos dañados pueden impedir que un sistema complete el proceso de inicio. En algunos escenarios de falla, el sistema sale del proceso de inicio y abre un shell de emergencia que requiere la contraseña del usuario root. La siguiente lista describe algunos problemas comunes de montaje del sistema de archivos al analizar el archivo /etc/fstab durante el proceso.

boot process:

Sistema de archivos dañado La unidad systemd intenta reparar el sistema de archivos. Si el problema no se puede reparar automáticamente, el sistema abre un shell de emergencia. Dispositivo de almacenamiento, UUID de dispositivo o punto de montaje inexistente. La unidad systemd agota el tiempo de espera a que el dispositivo de almacenamiento esté disponible. Si el dispositivo no responde, el sistema abre un caparazón de emergencia. Comprobación y reparación de daños en el sistema de archivos Red Hat Enterprise Linux 10 proporciona herramientas para comprobar y reparar problemas del sistema de archivos. En el caso de problemas menores que se detectan durante el arranque, estas utilidades intentan reparar el sistema de archivos automáticamente. Para los sistemas de archivos de diario, como XFS y ext4, puede que solo sea necesario reproducir el diario, lo que suele ser una operación rápida. En el caso de problemas de corrupción más graves del sistema de archivos, un administrador del sistema puede utilizar las herramientas para comprobar y reparar los sistemas de archivos manualmente. La herramienta que ayuda a mantener los sistemas de archivos en buen estado durante el arranque se conoce genéricamente como herramienta de verificación del sistema de archivos o comando fsck. Sin embargo, la herramienta que repara el sistema de archivos XFS no sigue la misma convención de nomenclatura. Aunque hay un archivo binario fsck.xfs en el sistema, su único propósito es satisfacer los requisitos de arranque y sale inmediatamente con un código de salida de 0. El comando xfs_repair puede verificar y reparar problemas con los sistemas de archivos XFS que una reparación automática no soluciona.

root@host:~# xfs_repair block-device

Para realizar operaciones de verificación y reparación en sistemas de archivos ext4, use el comando fsck.ext4, que es un enlace físico al comando e2fsck que también cubre los sistemas de archivos ext3 y ext2 heredados. Utilice la opción -p para reparar automáticamente problemas menores sin intervención del usuario.

root@host:~# mount --all
mount: /mnt/mountfolder: mount point does not exist.

En este escenario, donde el directorio /mnt/mountfolder no existe, cree el directorio /mnt/mountfolder antes de volver a intentar el montaje. Pueden aparecer otros mensajes de error, incluidos errores tipográficos en las entradas o nombres de dispositivos o UUID incorrectos. Después de corregir todos los problemas en el archivo /etc/fstab, informe al demonio systemd que registre el nuevo archivo /etc/fstab usando el comando systemctl daemon-reload.

root@host:~# systemctl daemon-reload

Luego, vuelva a intentar montar todas las entradas.

root@host:~# mount --all

La unidad systemd procesa el archivo /etc/fstab transformando cada entrada en un tipo de montaje y luego iniciando la unidad como un servicio. El comando systemctl daemon-reload solicita a la unidad systemd que reconstruya y recargue todas las configuraciones de la unidad. Si la opción --all del comando de montaje tiene éxito sin más errores, entonces la prueba final es verificar que los sistemas de archivos se monten correctamente durante el inicio del sistema. Reinicie el sistema y espere a que se complete el inicio.

root@host:~# systemctl reboot

Para una prueba rápida del archivo /etc/fstab, utilice la opción de entrada de montaje nofail. El uso de la opción nofail en una entrada /etc/fstab permite que el sistema arranque incluso si el montaje del sistema de archivos no tiene éxito. Esta opción no debe usarse con sistemas de archivos de producción que siempre deben montarse. Con la opción nofail, una aplicación podría iniciarse cuando faltan datos del sistema de archivos, con posibles consecuencias graves. 17.8. Resumen 17.8. Resumen En esta lección, aprendió sobre el proceso de inicio de Red Hat Enterprise Linux, cómo controlar qué servicios se inician en el inicio y cómo diagnosticar y reparar problemas del sistema de archivos durante el inicio. El cargador de arranque GRUB2 es el cargador de arranque predeterminado para RHEL 10. Es responsable de cargar el kernel y la imagen initramfs, y de pasar el control al kernel. GRUB2 también proporciona una interfaz de menú para seleccionar qué instancia de inicio iniciar y modificar la configuración de inicio en tiempo de ejecución. Puede utilizar el comando grubby para realizar diversas tareas de administración de inicio, como agregar o eliminar argumentos del kernel, cambiar la entrada predeterminada del menú de inicio y ver información sobre las entradas existentes del menú de inicio. La unidad systemd toma el control total de la última parte de la secuencia de inicio, según el objetivo predeterminado. El comando systemctl get-default proporciona información sobre el objetivo de unidad systemd predeterminado y el subcomando set-default establece un nuevo objetivo predeterminado. Los administradores pueden cambiar a un destino diferente durante el tiempo de ejecución utilizando el

systemctl isolate command.

El proceso de arranque podría verse interrumpido por un problema del sistema de archivos, como un sistema de archivos dañado o una configuración incorrecta del archivo /etc/fstab. El objetivo de emergencia arranca en un entorno mínimo que permite la resolución de problemas. El comando xfs_repair comprueba y repara problemas con los sistemas de archivos XFS. El archivo /etc/fstab puede incluir un dispositivo inexistente, lo que genera un error en el momento del arranque e interrumpe el proceso de arranque.

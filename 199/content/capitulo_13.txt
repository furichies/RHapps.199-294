# Capítulo 10. Control de servicios y demonios

## 10.1. Identificar procesos del sistema que se inician automáticamente

10.1. Identificación de procesos del sistema que se inician automáticamente 10.1. Identificación de procesos del sistema que se inician automáticamente Objetivos Enumerar los demonios del sistema y los servicios de red que se inician en el momento del arranque como servicios, o que se inician y se detienen dinámicamente cuando se establece una conexión de red. El demonio systemd El demonio systemd gestiona el proceso de inicio de Linux, que incluye el inicio de servicios y la gestión de servicios en general. El demonio systemd activa recursos del sistema, demonios del servidor y otros procesos, tanto en el momento del arranque como en un sistema en ejecución. Los demonios son procesos que esperan o se ejecutan en segundo plano para realizar diversas tareas. Por convención, los nombres de los demonios terminan en d, como httpd, vsftpd, chronyd, etc. En el contexto de systemd, un servicio a menudo se refiere a uno o más demonios. Generalmente, los demonios se inician automáticamente en el momento del arranque y continúan ejecutándose hasta que el sistema se apaga o hasta que los detienes manualmente. Sin embargo, iniciar o detener un servicio podría cambiar el estado del sistema una vez, sin dejar un proceso demonio en ejecución después (un tipo de servicio de una sola vez). En Red Hat Enterprise Linux, el primer proceso que se inicia (PID 1) es el demonio systemd, que proporciona estas características: Capacidades de paralelización (iniciar múltiples servicios simultáneamente), que aumentan la velocidad de arranque de un sistema. Inicio bajo demanda de demonios sin necesidad de un servicio independiente. Gestión automática de dependencias de servicios, que puede evitar tiempos de espera prolongados. Por ejemplo, un servicio dependiente de la red no intenta iniciarse hasta que la red esté disponible. Un método para rastrear procesos relacionados juntos mediante el uso de grupos de control de Linux. Descripción de unidades de servicio Una unidad systemd define objetos que el sistema sabe cómo gestionar. Las unidades están representadas por archivos de configuración denominados archivos de unidad, que encapsulan información sobre los servicios del sistema, los sockets de escucha y otros objetos relevantes para el sistema de inicio systemd. Una unidad tiene un nombre y un tipo de unidad. El nombre proporciona una identidad única a la unidad. El tipo de unidad permite agrupar unidades con otros tipos de unidades similares. El demonio systemd utiliza unidades para gestionar diferentes tipos de objetos: Unidades de servicio Las unidades de servicio tienen una extensión .service y representan servicios del sistema. Puede utilizar unidades de servicio para iniciar demonios utilizados con frecuencia, como un servidor web. Unidades de zócalo Las unidades de zócalo tienen una extensión .socket y representan sockets de comunicación entre procesos (IPC) que systemd debe monitorear. Si un cliente se conecta al socket, entonces el administrador systemd inicia un demonio y le pasa la conexión. Puede utilizar unidades de socket para retrasar el inicio de un servicio en el momento del arranque y para iniciar bajo demanda los servicios que se utilizan con menos frecuencia.

Identificación de procesos del sistema que se inician automáticamente Unidades de ruta Las unidades de ruta tienen una extensión .path y retrasan la activación de un servicio hasta que ocurre un cambio específico en el sistema de archivos. Puede utilizar unidades de ruta para servicios que utilizan directorios de spool, como un sistema de impresión. Para administrar unidades, use el comando systemctl. Por ejemplo, muestre los tipos de unidades disponibles con el comando systemctl -t help. El comando systemctl puede tomar nombres de unidades abreviados, entradas del árbol de procesos y descripciones de unidades. root@host:~# systemctl is-enabled sshd.service

root@host:~# systemctl is-failed sshd.service

activo El comando regresa activo si el servicio se está ejecutando correctamente, o falla si ocurrió un error durante el inicio. Si la unidad se detuvo, regresa desconocida o inactiva. Para enumerar todas las unidades fallidas, ejecute el comando systemctl --failed --type=service. Para verificar el estado de un servicio, incluido si el servicio se está ejecutando o detenido, use el estado systemctl

command:
root@host:~# systemctl status sshd.service

● sshd.service: demonio del servidor OpenSSH

     Loaded: loaded (/usr/lib/systemd/system/sshd.service; enabled; preset: enabled)

...salida omitida... Para iniciar un servicio, utilice el comando systemctl start como usuario root (con el comando sudo si es necesario). Si ejecuta el comando systemctl start solo con el nombre del servicio (sin el tipo de servicio), entonces el servicio systemd busca archivos .service.

root@host:~# systemctl start sshd

Para detener un servicio en ejecución, utilice la opción de detención del comando systemctl. El siguiente ejemplo detiene el

sshd.service service:
root@host:~# systemctl stop sshd.service

Reinicio y recarga de servicios Cuando reinicia un servicio en ejecución, el servicio primero se detiene y luego se reinicia. Al reiniciar el servicio, el nuevo proceso obtiene una nueva ID durante el inicio y, por lo tanto, la ID del proceso cambia. Para reiniciar un servicio en ejecución, use la opción de reinicio del comando systemctl. El siguiente ejemplo reinicia el sshd

service:
root@host:~# systemctl restart sshd.service

Algunos servicios pueden recargar sus archivos de configuración sin necesidad de reiniciar, lo que se denomina recarga del servicio. Recargar un servicio no cambia el ID de proceso asociado con varios procesos de servicio. Para recargar un servicio en ejecución, use la opción de recarga del comando systemctl. El siguiente ejemplo muestra cómo recargar el servicio sshd.service

after configuration changes:
root@host:~# systemctl reload sshd.service

Si no está seguro de si el servicio tiene la función para recargar los cambios del archivo de configuración, use la opción recargar o reiniciar del comando systemctl. El comando recarga los cambios de configuración si la función de recarga está

Listado de dependencias de unidades Algunos servicios requieren que otros servicios se ejecuten primero, lo que crea dependencias en los otros servicios. Algunos servicios se inician sólo a pedido, en lugar de en el momento del arranque. En ambos casos, los comandos systemd y systemctl inician los servicios según sea necesario, ya sea para resolver la dependencia o para iniciar un servicio que se utiliza con poca frecuencia. Deshabilitar el servicio deshabilita las dependencias. Para ver una asignación jerárquica de dependencias para iniciar una unidad de servicio, utilice el comando systemctl list-dependencies UNIT. El siguiente ejemplo enumera las dependencias para el servicio sshd.service:

root@host:~# systemctl list-dependencies sshd.service

root@host:~# systemctl list-dependencies --reverse NetworkManager.service

Un ejemplo común es cuando dos servicios requieren el mismo puerto de red. Por ejemplo, tanto el servidor HTTP Apache como el servidor web nginx utilizan el puerto 80 para escuchar el tráfico HTTP. Para evitar conflictos, puede enmascarar uno de los servicios utilizando el comando systemctl mask. Enmascarar un servicio crea un enlace simbólico desde la unidad de servicio al archivo /dev/null, lo que impide que un administrador inicie el servicio. root@host:~# systemctl mask httpd.service

Habilitar servicios para que se inicien o se detengan al arrancar Iniciar un servicio en un sistema en ejecución no garantiza que el servicio se inicie automáticamente cuando se reinicie el sistema. De manera similar, detener un servicio en un sistema en ejecución no impide que se reinicie cuando el sistema se reinicie. La creación de enlaces en los directorios de configuración de systemd permite que el servicio se inicie en el arranque. Puede crear o eliminar estos enlaces utilizando el comando systemctl con la opción habilitar o deshabilitar.

root@root:~# systemctl enable sshd.service

Se creó el enlace simbólico '/etc/systemd/system/multi-user.target.wants/sshd.service' → '/usr/lib/systemd/system/sshd.service'. Este comando crea un enlace simbólico desde el archivo de la unidad de servicio, generalmente en el directorio /usr/lib/systemd/system, a la ubicación del disco donde el comando systemd busca archivos, en el directorio /etc/systemd/system/TARGETNAME.target.wants. Habilitar un servicio no inicia el servicio en la sesión actual. Para iniciar el servicio y permitir que se inicie automáticamente durante el arranque, puede ejecutar tanto el

systemctl start and systemctl enable commands, or use the equivalent systemctl enable --now

dominio.

root@root:~# systemctl enable --now sshd.service

Se creó el enlace simbólico '/etc/systemd/system/multi-user.target.wants/sshd.service' → '/usr/lib/systemd/system/sshd.service'. Para impedir que el servicio se inicie automáticamente, utilice el comando systemctl enable, que elimina el enlace simbólico que se creó al habilitar un servicio. Deshabilitar un servicio no lo detiene si se está ejecutando actualmente. Para deshabilitar y detener un servicio, puede ejecutar los comandos systemctl stop y systemctl enable, o usar el comando systemctl enable --now equivalente.

Puede administrar cada demonio configurando su configuración de inicio automático o iniciando, deteniendo y reiniciando el demonio. La utilidad systemd también gestiona unidades de servicio, unidades de socket y unidades de ruta. Puede enmascarar una unidad de servicio para que no se ejecute, incluso para satisfacer dependencias.

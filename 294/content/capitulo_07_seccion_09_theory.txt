Reutilización de contenido con roles de
sistema
Objetivos
• Escribir playbooks que aprovechen los roles del sistema de Red Hat Enterprise Linux para
realizar operaciones estándares.
Roles de sistema
Roles del sistema son un conjunto de roles de Ansible que puede usar para configurar y gestionar
diversos componentes, subsistemas y paquetes de software incluidos en Red Hat Enterprise
Linux. Los roles del sistema proporcionan automatización para muchas tareas comunes de
configuración del sistema, incluida la sincronización de la hora, las redes, el firewall, el ajuste y el
registro.
Estos roles están destinados a proporcionar una API de automatización que sea uniforme en
varias versiones principales y secundarias de Red Hat Enterprise Linux. El artículo de la base
de conocimiento en https://access.redhat.com/articles/3050101 documenta las
versiones de Red Hat Enterprise Linux en sus hosts gestionados que admiten roles específicos.
Gestión simplificada de la configuración
Los roles del sistema pueden ayudarlo a simplificar la automatización en varias versiones de
Red Hat Enterprise Linux. Por ejemplo, el servicio de sincronización de hora recomendado es
diferente en diferentes versiones de Red Hat Enterprise Linux.
• Se prefiere el servicio chronyd en RHEL 9.
• Se prefiere el servicio ntpd en RHEL 6.
En un entorno con una combinación de versiones de Red Hat Enterprise Linux, debe gestionar los
archivos de configuración para ambos servicios.
Puede usar un playbook de Ansible que ejecute el rol redhat.rhel_system_roles.timesync
para configurar la sincronización de la hora para los hosts gestionados que ejecutan cualquiera de
las versiones de Red Hat Enterprise Linux.
Con los roles del sistema, ya no necesita mantener los archivos de configuración para ambos
servicios.
Soporte para roles de sistema
Los roles del sistema se proporcionan como Ansible Content Collections
redhat.rhel_system_roles certificadas por Red Hat a través del centro de automatización
para los clientes de Red Hat Ansible Automation Platform, como parte de su suscripción.
Además, los roles se proporcionan como un paquete RPM (rhel-system-roles) con Red Hat
Enterprise Linux 9 para su uso con la versión de Ansible Core proporcionada por ese sistema
operativo. Estos roles del sistema tienen los mismos beneficios de soporte de ciclo de vida que la
suscripción a Red Hat Enterprise Linux.
La mayoría de los roles de sistema son "totalmente soportados" y tienen interfaces estables.

Instalación de Ansible Content Collection de los roles
del sistema
Puede instalar Ansible Content Collection redhat.rhel_system_roles con el comando
ansible-galaxy collection install. Un proyecto de Ansible puede especificar esta
dependencia creando un archivo collections/requirements.yml. En el siguiente ejemplo,
se supone que su proyecto está configurado para extraer Ansible Content Collections del centro
de automatización.
---
collections:
  - name: redhat.rhel_system_roles
El siguiente comando instala las colecciones necesarias para un proyecto determinado en el
directorio collections/ del proyecto.
[user@demo demo-project]$ ansible-galaxy collection \
> install -p collections/ -r collections/requirements.yml

Ejemplo: rol de sincronización de tiempos
Supongamos que necesita configurar la sincronización temporal de NTP en sus servidores web.
Podría escribir la automatización usted mismo para realizar cada una de las tareas necesarias.
Pero la colección de roles del sistema incluye un rol que puede realizar la configuración,

En la documentación de este rol se describen todas las variables que afectan el comportamiento

Para configurar manualmente los servidores NTP, el rol tiene una variable llamada
timesync_ntp_servers. Esta variable define una lista de servidores NTP para usar. Cada ítem
de la lista se compone de uno o más atributos. Los dos atributos clave son hostname y iburst.
Atributo
Propósito
hostname
El nombre de host de un servidor NTP con el que se puede
sincronizar.
iburst
Un valor booleano que habilita o deshabilita la sincronización
inicial rápida. Se establece de forma predeterminada en no en el
rol; normalmente debe establecerse en yes.
Dada esta información, el siguiente ejemplo es un play que usa el rol
redhat.rhel_system_roles.timesync para configurar los hosts gestionados a fin de
obtener el tiempo de tres servidores NTP usando la sincronización inicial rápida.
- name: Time Synchronization Play
  hosts: webservers
  vars:
    timesync_ntp_servers:
      - hostname: 0.rhel.pool.ntp.org
        iburst: yes
      - hostname: 1.rhel.pool.ntp.org
        iburst: yes
      - hostname: 2.rhel.pool.ntp.org
        iburst: yes
  roles:
    - redhat.rhel_system_roles.timesync
Este ejemplo establece las variables de rol en una sección vars del play, pero una mejor práctica
sería configurarlas como variables de inventario para hosts o grupos de hosts.
Considere un proyecto de guía con la siguiente estructura:

- name: Time Synchronization Play
  hosts: webservers
  roles:
    - redhat.rhel_system_roles.timesync
Esta estructura separa claramente el rol, el código del playbook y los ajustes de configuración. El
código del playbook es simple, fácil de leer y no debe requerir una refactorización compleja. El
contenido de rol es mantenido y soportado por Red Hat. Todas las configuraciones se manejan
como variables de inventario.
Esta estructura también soporta un entorno dinámico y heterogéneo. Los hosts con nuevos
requisitos de sincronización temporal se pueden colocar en un nuevo grupo de hosts. Las variables
apropiadas se definen en un archivo YAML y se colocan en el subdirectorio correspondiente
group_vars (o host_vars).
Ejemplo: rol de SELinux
Como otro ejemplo, el rol redhat.rhel_system_roles.selinux simplifica la administración
de ajustes de configuración de SELinux. Este rol se implementa usando los módulos de Ansible
relacionados con SELinux. La ventaja de usar este rol en lugar de escribir sus propias tareas es que
lo exime de la responsabilidad de escribir esas tareas. En su lugar, proporciona variables al rol para
configurarlo, y el código mantenido en el rol garantizará que se aplique la configuración deseada
de SELinux.
Este rol puede ejecutar las siguientes tareas:
• Establecer el modo de ejecución o permisivo
• Ejecutar restorecon en partes de la jerarquía del sistema de archivos
• Configurar valores booleanos de SELinux
• Configurar de manera persistente los contextos de archivos de SELinux
• Configurar asignaciones de usuarios de SELinux
Llamada al rol de SELinux
A veces, el rol SELinux debe garantizar que los hosts gestionados se reinicien para aplicar
completamente los cambios. Sin embargo, el rol nunca reinicia los hosts, lo que le permite
controlar cómo se maneja el reinicio. Por lo tanto, es un poco más complicado de lo habitual usar
correctamente este rol en un play.
El rol establecerá una variable booleana, selinux_reboot_required, en true y fallará si se
necesita un reinicio. Puede usar una estructura block/rescue para recuperarse de la falla, ya
sea que falle el play si la variable no se configura en true o reinicia el host gestionado y vuelve a
ejecutar el rol si está en true. El bloque en su play debe verse parecido a lo siguiente:

Configuración del rol de SELinux
Las variables usadas para configurar el rol redhat.rhel_system_roles.selinux se
describen en la documentación del rol. En los siguientes ejemplos, se muestran algunas formas de
usar este rol.
La variable selinux_state establece el modo en que se ejecuta SELinux. Puede establecerse
en enforcing, permissive o disabled. Si no está configurada, el modo no se cambia.
selinux_state: enforcing
La variable selinux_booleans toma una lista de valores booleanos de SELinux para ajustarse.
Cada ítem de la lista es un diccionario de variables: name del booleano, state (tanto en on como
en off), e independientemente de que el ajuste deba ser persistent en los reinicios.
Este ejemplo establece httpd_enable_homedirs en on continuamente:
selinux_booleans:
  - name: 'httpd_enable_homedirs'
    state: 'on'
    persistent: 'yes'
La variable selinux_fcontexts requiere una lista de contextos de archivo para establecerse
continuamente (o eliminarse) y funciona de manera similar al comando selinux fcontext.
En el siguiente ejemplo, se garantiza que la política tenga una regla para establecer el tipo de
SELinux predeterminado para todos los archivos de /srv/www en httpd_sys_content_t.
selinux_fcontexts:
  - target: '/srv/www(/.*)?'
    setype: 'httpd_sys_content_t'
    state: 'present'

Uso de roles del sistema solo con Ansible Core
nota
Esta sección es relevante si planea usar roles del sistema sin una suscripción a
Red Hat Ansible Automation Platform, mediante el uso de la versión de Ansible Core
que se proporciona con Red Hat Enterprise Linux 9.
Si no tiene una suscripción a Red Hat Ansible Automation Platform, pero tiene sistemas Red Hat
Enterprise Linux, puede usar roles de sistema con la versión de Ansible Core proporcionada con
RHEL.
Esa versión de Ansible Core solo es compatible con roles del sistema y otro código de
automatización proporcionado por Red Hat. Además, no incluye ansible-navigator, por lo
que debe usar herramientas como ansible-playbook que tratan su nodo de control como el
entorno de ejecución para ejecutar su automatización.
Debido a que ansible-playbook no usa entornos de ejecución, la única Ansible Content
Collection que tiene disponible de forma predeterminada es la colección ansible.builtin.
Otros paquetes incluidos en Red Hat Enterprise Linux pueden agregar Ansible Content
Collections adicionales al nodo de control.
Instalación del paquete RPM de roles del sistema
Asegúrese de que su nodo de control esté registrado con Red Hat Subscription Manager y tenga
una suscripción a Red Hat Enterprise Linux. También debe instalar el paquete RPM ansible-
core.
Para instalar el paquete RPM rhel-system-roles, asegúrese de que el repositorio de paquetes
de AppStream esté habilitado. Para Red Hat Enterprise Linux 9 en la arquitectura del procesador
x86_64, este es el repositorio rhel-9-for-x86_64-appstream-rpms. Luego puede instalar
instale el paquete.
[user@controlnode ~]$ sudo dnf install rhel-system-roles

El nombre upstream correspondiente de cada rol está vinculado al rol de sistema RHEL. Esto

Importante
Si está usando ansible-playbook para ejecutar su playbook y este hace
referencia a un rol del sistema que se instaló usando el FQCN del paquete RPM,
debe usar la versión redhat.rhel_system_roles de su nombre. Por ejemplo,
puede hacer referencia al rol firewall como:
• redhat.rhel_system_roles.firewall (su FQCN en la colección)
• rhel-system-roles.firewall (su nombre como rol independiente)
• linux-system-roles.firewall (su nombre como rol independiente
upstream)
No puede usar fedora.linux_system_roles.firewall porque la colección
fedora.linux_system_roles no está instalada en el sistema.
Además, los nombres de roles independientes solo funcionan si /usr/share/
ansible/roles está en su configuración roles_path.

Ejecución de playbooks sin el navegador de contenido de
automatización
Puede usar el comando ansible-playbook para ejecutar un playbook que usa roles de sistema
en Red Hat Enterprise Linux cuando no tiene Red Hat Ansible Automation Platform o ansible-
navigator.
La sintaxis de ansible-playbook es muy similar a ansible-navigator run -m stdout y
toma muchas de las mismas opciones.
[user@controlnode ~]$ ansible-playbook playbook.yml

Ejercicio Guiado
Reutilización de contenido con roles de
sistema
Usar uno de los roles de sistema junto con tareas para configurar la sincronización temporal y
la zona horaria de los hosts gestionados.
Resultados
• Instalar los roles de sistema de Red Hat Enterprise Linux.
• Buscar y usar la documentación de roles de sistema.
• Usar el rol redhat.rhel_system_roles.timesync en un playbook para configurar la
sincronización temporal en hosts remotos.
Antes De Comenzar
Con el usuario student en la máquina workstation, use el comando lab para preparar su
sistema para este ejercicio.
Este comando prepara su entorno y garantiza que estén disponibles todos los recursos
requeridos.
[student@workstation ~]$ lab start role-system
Instrucciones
 1.
Cambie al directorio /home/student/role-system.
[student@workstation ~]$ cd ~/role-system
[student@workstation role-system]$
 2.
Instale los roles del sistema en su nodo de control, workstation.lab.example.com.
Confirme que los roles del sistema se hayan instalado mediante ansible-galaxy.
2.1.
Use el comando ansible-galaxy collection list para mostrar las
colecciones instaladas.
[student@workstation role-system]$ ansible-galaxy collection list
2.2.
Cree el directorio collections.
[student@workstation role-system]$ mkdir -p collections
2.3.
El directorio ./collections no es una ubicación de búsqueda predeterminada para
las colecciones. Agregue la clave collections_paths al archivo ansible.cfg, de
modo que se busque en el directorio ./collections.

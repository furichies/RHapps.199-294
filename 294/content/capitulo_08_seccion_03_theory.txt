Solución de problemas en hosts
gestionados de Ansible
Objetivos
• Solucionar fallas en hosts gestionados cuando se ejecuta un playbook.
Solución de problemas de conexiones
Muchos problemas comunes al usar Ansible para administrar hosts están asociados con
conexiones al host y con problemas de configuración relacionados con el usuario remoto y el
aumento de privilegios.
Problemas de autenticación en hosts gestionados
Si tiene problemas para autenticarse en un host gestionado, asegúrese de tener remote_user
correctamente configurado en el archivo de configuración o en el play.
Por ejemplo, es posible que vea la siguiente salida al ejecutar un playbook diseñado para
conectarse a la cuenta de usuario remota root:
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Install a samba server] **************************************************
TASK [Gathering Facts] *********************************************************
fatal: [host.lab.example.com]: UNREACHABLE! => {"changed": false, "msg":
 "Failed to connect to the host via ssh: developer@host: Permission denied
 (publickey,gssapi-keyex,gssapi-with-mic,password).", "unreachable": true}
PLAY RECAP *********************************************************************
host.lab.example.com    : ok=0    changed=0    unreachable=1    failed=0   
 skipped=0    rescued=0    ignored=0
Please review the log for errors.
En este caso, ansible-navigator está intentando conectarse como la cuenta de usuario
developer, de acuerdo con la salida anterior. Una razón por la que esto puede suceder es si
se ha configurado ansible.cfg en el proyecto para establecer el remote_user en el usuario
developer en lugar del usuario root.
Otra razón por la que puede ver un error de "permiso denegado" como este es si no tiene
configuradas las claves SSH correctas o no proporcionó la contraseña correcta para ese usuario.
[root@controlnode ~]# ansible-navigator run \
> -m stdout playbook.yml
TASK [Gathering Facts] *********************************************************
fatal: [host.lab.example.com]: UNREACHABLE! => {"changed": false, "msg": "Failed
 to connect to the host via ssh: root@host: Permission denied (publickey,gssapi-
keyex,gssapi-with-mic).", "unreachable": true}

Problemas con la resolución de nombres o direcciones
Un problema más sutil tiene que ver con la configuración del inventario. Para un servidor complejo
con varias direcciones de red, es posible que deba usar una dirección particular o un nombre
DNS al conectarse a ese sistema. Es posible que no desee utilizar esa dirección como nombre de
inventario de la máquina para una mejor legibilidad. Puede configurar una variable de inventario
de host, ansible_host, que anule el nombre del inventario con un nombre o una dirección IP
diferente y será usado por Ansible para conectarse a ese host. Esta variable podría configurarse en
el archivo o directorio host_vars para ese host o en el propio archivo de inventario.
Por ejemplo, la siguiente entrada de inventario configura Ansible para conectarse a 192.0.2.4 al
procesar el host web4.phx.example.com:
web4.phx.example.com ansible_host=192.0.2.4
Esta es una forma útil de controlar cómo Ansible se conecta a los hosts gestionados. Sin embargo,
también puede causar problemas si el valor de ansible_host es incorrecto.
Problemas con el aumento de privilegios
Si su playbook se conecta como remote_user y luego usa el aumento de privilegios para
convertirse en el usuario root (o algún otro usuario), asegúrese de que become esté configurado
correctamente y de que esté usando el valor correcto para la directiva become_user. La
configuración de become_user es root de forma predeterminada.
Si el usuario remoto debe proporcionar una contraseña sudo, usted debe confirmar que está
ingresando la contraseña sudo correcta y que sudo en el host gestionado esté configurado
correctamente.

> -m stdout playbook.yml

Importante
Normalmente, ansible-navigator se ejecuta como root dentro de su entorno
de ejecución de automatización. Sin embargo, el usuario root en el contenedor
tiene acceso a las claves SSH proporcionadas por el usuario que ejecutó ansible-
navigator en la estación de trabajo. Esto puede ser un poco confuso cuando
intenta depurar las directivas remote_user y become, especialmente si está
acostumbrado al comando ansible-playbook anterior que se ejecuta como el
usuario en la estación de trabajo.
Problemas con Python en hosts gestionados

hosts gestionados que ejecutan Linux. Ansible intenta ubicar un intérprete de Python en cada host

Uso del modo de verificación como herramienta de
prueba
Puede usar el comando ansible-navigator run --check para ejecutar "pruebas de
humo" en un playbook. Esta opción ejecuta el playbook y se conecta a los hosts gestionados
normalmente, pero sin realizar cambios en ellos.
Si un módulo usado dentro del playbook soporta el "modo de verificación", se muestran los
cambios que se habrían realizado en los hosts gestionados (pero que no se hicieron). Si un módulo
no soporta el modo de verificación, ansible-navigator no muestra los cambios previstos, pero
el módulo aún no realiza ninguna acción.
[student@demo ~]$ ansible-navigator run \
> -m stdout playbook.yml --check
Importante
El comando ansible-navigator run --check podría no funcionar
correctamente si las tareas usan condicionales. Una razón para esto podría ser
que los condicionales dependen de alguna tarea anterior en el play que se está
ejecutando realmente para que la condición se evalúe correctamente.
Puede forzar que las tareas se ejecuten siempre en modo de verificación o que siempre se
ejecuten normalmente con la configuración check_mode. Si una tarea tiene check_mode:
true establecida, siempre se ejecuta en su modo de verificación y no realiza ninguna acción,
incluso si no pasa la opción --check a ansible-navigator. Del mismo modo, si una tarea tiene
configurado check_mode: false, siempre se ejecuta normalmente, incluso si pasa --check a
ansible-navigator.
La siguiente tarea siempre se ejecuta en modo de verificación y no realiza cambios a los hosts
gestionados.
  tasks:
    - name: task always in check mode
      ansible.builtin.shell: uname -a
      check_mode: true
La siguiente tarea siempre se ejecuta normalmente, incluso cuando se inicia con ansible-
navigator run --check.
  tasks:
    - name: task always runs even in check mode
      ansible.builtin.shell: uname -a
      check_mode: false
Esto puede ser útil porque puede ejecutar la mayor parte de un playbook normalmente y probar
tareas individuales con check_mode: true. Muchos plays usan datos o establecen variables
para ejecutar tareas de manera condicional. Las tareas condicionales pueden fallar si un dato o
una variable no está definida, debido a que la tarea que las recopila o establece no se ejecuta
en un nodo administrado. Puede usar check_mode: false en tareas que recopilan datos
o establecen variables, pero que no cambian el nodo administrado. Esto permite que el play
continúe cuando se usa el modo --check.

Una tarea puede determinar si el playbook se está ejecutando en modo de verificación probando
el valor de la variable mágica ansible_check_mode. Esta variable booleana se establece en
true si el playbook se está ejecutando en modo de verificación.
Advertencia
Las tareas que tienen configurado check_mode: false se ejecutarán incluso
cuando el playbook se ejecute con ansible-navigator run --check. Por lo
tanto, no se puede confiar en que la opción --check no realizará cambios en los
hosts gestionados, sin inspeccionar el playbook y los roles o tareas asociados con
este.
nota
Si tiene playbooks más antiguos que usan always_run: true para forzar a las
tareas a ejecutarse normalmente, incluso en el modo de verificación, tendrá que
reemplazar ese código con check_mode: false en Ansible 2.6 y posteriores.
El comando ansible-navigator también proporciona una opción --diff. Esta opción informa
los cambios realizados a los archivos de plantillas en hosts gestionados. Si se usan con la opción
--check, estos cambios se muestran en la salida del comando, pero no se realizan.
[student@demo ~]$ ansible-navigator run \
> -m stdout playbook.yml --check --diff
Pruebas con módulos
Algunos módulos pueden brindar información adicional acerca de cuál es el estado de un host
gestionado. La siguiente lista incluye algunos de los módulos de Ansible que se pueden usar para
probar y depurar problemas en hosts gestionados.
El módulo ansible.builtin.uri aporta una forma de verificar que una RESTful API esté
devolviendo el contenido requerido.
  tasks:
    - ansible.builtin.uri:
        url: http://api.myapp.example.com
        return_content: true
      register: apiresponse
    - ansible.builtin.fail:
        msg: 'version was not provided'
      when: "'version' not in apiresponse.content"
El módulo ansible.builtin.script ejecuta un script en hosts gestionados y falla si el código
de retorno para el script es diferente a cero. El script debe estar en el proyecto de Ansible y se
transferirá y ejecutará en el host gestionado.
  tasks:
    - ansible.builtin.script: scripts/check_free_memory --min 2G

El módulo ansible.builtin.stat recopila datos para un archivo muy similar al comando
stat. Puede usarlo para registrar una variable y luego hacer una prueba para determinar si
el archivo existe, o para obtener otra información sobre el archivo. Si el archivo no existe, la
tarea ansible.builtin.stat no fallará, pero su variable registrada informará false para
*['stat']['exists'].
En este ejemplo, todavía se está ejecutando una aplicación si existe /var/run/app.lock, en
cuyo caso el play deberá abortar.
  tasks:
    - name: Check if /var/run/app.lock exists
      ansible.builtin.stat:
        path: /var/run/app.lock
      register: lock
    - name: Fail if the application is running
      ansible.builtin.fail:
      when: lock['stat']['exists']
El módulo ansible.builtin.assert es una alternativa al módulo ansible.builtin.fail.
El módulo ansible.builtin.assert soporta una opción that que toma una lista de
condicionales. Si alguno de esos condicionales es falso, la tarea falla. Puedes usar las opciones
success_msg y fail_msg para personalizar el mensaje que imprime si informa éxito o fracaso.
El siguiente ejemplo repite el anterior, pero usa ansible.builtin.assert en lugar de
ansible.builtin.fail.
  tasks:
    - name: Check if /var/run/app.lock exists
      ansible.builtin.stat:
        path: /var/run/app.lock
      register: lock
    - name: Fail if the application is running
      ansible.builtin.assert:
        that:
          - not lock['stat']['exists']
Ejecución de comandos ad hoc con Ansible
Un comando ad hoc es una manera de ejecutar una sola tarea de Ansible con rapidez; una que no
necesite guardar para ejecutarse nuevamente más tarde. Son operaciones simples, en línea, que
pueden ejecutarse sin escribir un playbook.
Los comandos ad hoc no se ejecutan dentro de un contenedor de entorno de ejecución de
automatización. En su lugar, se ejecutan con el software, los roles y las colecciones de Ansible
instalados directamente en su estación de trabajo. Para usar comandos ad hoc de Ansible
Core 2.13, debe instalar el paquete RPM ansible-core en su estación de trabajo.
Importante
El paquete RPM ansible-core proporciona solo los módulos en Ansible Content
Collection ansible.builtin. Si necesita módulos de otras colecciones, debe
instalarlos en su estación de trabajo por separado.

Los comandos ad hoc son útiles para pruebas rápidas y solucionar problemas. Por ejemplo, puede
usar un comando ad hoc para asegurarse de que los hosts sean accesibles mediante el módulo
ansible.builtin.ping. Puede usar otro comando ad hoc para ver el uso de recursos en un
grupo de hosts usando el módulo ansible.builtin.command.
Los comandos ad hoc tienen sus límites y, en general, se recomienda usar playbooks de Ansible
para desarrollar la potencia máxima de Ansible.
Use el comando ansible para ejecutar comandos ad hoc:
[user@controlnode ~]$ ansible host-pattern -m module [-a 'module arguments'] \
> [-i inventory]
El argumento host-pattern se usa para especificar los hosts gestionados en los cuales se
debería ejecutar el comando ad hoc. La opción -i se usa para especificar una ubicación diferente
del inventario para usar en lugar de la predeterminada en el archivo de configuración actual de
Ansible. La opción -m especifica el módulo que Ansible debería ejecutar en los hosts de destino.
La opción -a toma una lista de argumentos para el módulo como cadena entre comillas.
nota
Si usa el comando ansible, pero no especifica un módulo con la opción -m, el
módulo ansible.builtin.command se usa de manera predeterminada. Siempre
es mejor especificar el módulo que desea usar, incluso si tiene la intención de usar el
módulo ansible.builtin.command.
Los comandos ad hoc de Ansible pueden ser útiles, pero deben mantenerse para la resolución
de problemas y los casos de uso únicos. Por ejemplo, si tiene conocimiento de varios cambios de
red pendientes, es más eficiente crear un playbook con una tarea ansible.builtin.ping que
puede ejecutar varias veces, en comparación con escribir un comando ad hoc de uso único varias
veces.

Escritura de bucles y tareas condicionales
Objetivos
• Usar bucles para escribir tareas eficientes y condiciones para controlar cuándo ejecutar tareas.
Iteración de tareas con bucles
El uso de bucles permite evitar escribir varias tareas que usan el mismo módulo. Por ejemplo, en
lugar de escribir cinco tareas para garantizar que existan cinco usuarios, puede escribir una tarea
que itere sobre una lista de cinco usuarios para garantizar que existan todos.
Para iterar una tarea sobre un conjunto de ítems, puede usar la palabra clave loop. Puede
configurar los bucles para que repitan una tarea con cada ítem en una lista, el contenido de cada
uno de los archivos en una lista, una secuencia de números generada o con estructuras más
complicadas.
En esta sección, se cubren bucles simples que iteran sobre una lista de ítems. Consulte la
documentación para ver escenarios de bucle más avanzados.
Bucles simples
Un bucle simple itera una tarea sobre una lista de ítems. Se agrega la palabra clave loop a la tarea,
y esta toma como valor la lista de ítems sobre los cuales se debería iterar la tarea. La variable de
bucle item contiene el valor usado durante cada iteración.
Considere el siguiente fragmento que usa el módulo ansible.builtin.service dos veces
para garantizar que se estén ejecutando dos servicios de red:
- name: Postfix is running
  ansible.builtin.service:
    name: postfix
    state: started
- name: Dovecot is running
  ansible.builtin.service:
    name: dovecot
    state: started
Estas dos tareas pueden reescribirse para usar un bucle simple, de modo que se necesita solo una
tarea para garantizar que se ejecuten ambos servicios:
- name: Postfix and Dovecot are running
  ansible.builtin.service:
    name: "{{ item }}"
    state: started
  loop:
    - postfix
    - dovecot

El bucle puede usar una lista provista por una variable.
En el siguiente ejemplo, la variable mail_services contiene la lista de servicios que se deben
ejecutar.
vars:
  mail_services:
    - postfix
    - dovecot
tasks:
  - name: Postfix and Dovecot are running
    ansible.builtin.service:
      name: "{{ item }}"
      state: started
    loop: "{{ mail_services }}"
Bucles sobre una lista de diccionarios
La lista loop no necesita ser una lista de valores simples.
En el siguiente ejemplo, cada ítem en la lista es en realidad un diccionario. Cada diccionario del
ejemplo tiene dos claves, name y groups, y el valor de cada clave en la variable de bucle item
actual puede obtenerse con las variables item['name'] y item['groups'], respectivamente.
- name: Users exist and are in the correct groups
  user:
    name: "{{ item['name'] }}"
    state: present
    groups: "{{ item['groups'] }}"
  loop:
    - name: jane
      groups: wheel
    - name: joe
      groups: root
El resultado de la tarea anterior es que el usuario jane está presente y es un miembro del grupo
wheel, y el usuario joe está presente y es un miembro del grupo root.

loop.

filtros Ansible. No necesita saber cómo usar los filtros Ansible para hacer esto. La documentación

Ansible.
Es probable que encuentre tareas de playbooks anteriores que contienen palabras clave with_*.
Las técnicas avanzadas de bucle están fuera del alcance de este curso. Todas las tareas de
iteración en este curso se pueden implementar ya sea con la palabra clave with_items o loop.

Ejecución de tareas de forma condicional
Ansible puede usar condicionales para ejecutar tareas o plays cuando se cumplen ciertas
condiciones. Por ejemplo, puede usar un condicional para determinar la memoria disponible en un
host gestionado antes de que Ansible instale o configure un servicio.

asignen roles funcionales según las condiciones que cumplen. Las variables del playbook, las

variables registradas y los datos de Ansible se pueden probar con condicionales. Los operadores
para comparar cadenas, datos numéricos y valores booleanos están disponibles.
Los siguientes escenarios ilustran el uso de condicionales en Ansible.
• Defina un límite de hardware en una variable (por ejemplo, min_memory) y compárelo con la
memoria disponible en un host gestionado.
• Capture la salida de un comando y evalúela para determinar si se completó una tarea antes de
tomar otras medidas. Por ejemplo, si falla un programa, se omite un lote.
• Use los datos de Ansible para determinar la configuración de la red del host gestionado y decida
qué archivo de plantilla enviar (por ejemplo, unificación o enlace troncal de red).
• Evalúe el número de CPU para determinar cómo ajustar adecuadamente un servidor web.
• Compare una variable registrada con una variable predefinida para determinar si un servicio
cambió. Por ejemplo, pruebe la suma de comprobación MD5 de un archivo de configuración de
servicio para ver si se modifica el servicio.
Sintaxis condicional de tareas
El enunciado when se usa para ejecutar una tarea de forma condicional. Toma como valor la
condición para realizar pruebas. Si se cumple la condición, se ejecuta la tarea. Si no se cumple la
condición, se omite la tarea.
Una de las condiciones más simples que pueden probarse es si una variable booleana es
verdadera o falsa. El enunciado when en el siguiente ejemplo hace que la tarea se ejecute solo si
run_my_task es verdadero.
---
- name: Simple Boolean Task Demo
  hosts: all
  vars:
    run_my_task: true
  tasks:
    - name: httpd package is installed
      ansible.builtin.dnf:
        name: httpd
      when: run_my_task

nota
Las variables booleanas pueden tener el valor true o false.
En el contenido de Ansible, puede expresar esos valores de otras formas: True,
yes o 1 también se aceptan para true; y False, no o 0 también se aceptan para
false. Es posible que vea true y yes, o false y no usados indistintamente para
expresar valores booleanos en el contenido de Ansible existente.
Los archivos YAML de Ansible se basan en el estándar YAML 1.1, pero el estándar
YAML 1.2 especifica que solo puede usar true o false para establecer valores
booleanos. Por esta razón, es posible que vea una estandarización gradual hacia el
uso solo de true o false para los valores booleanos en playbooks y otros archivos
de Ansible, aunque las formas equivalentes de expresar esos valores siguen siendo
válidas. Si Ansible eventualmente debiera usar solo esas formas de expresar los
valores booleanos es una pregunta abierta y una discusión en curso en la comunidad
de Ansible.
Importante
Al usar condiciones de verdadero/falso, como en el ejemplo anterior, debe tener
mucho cuidado de asegurarse de que Ansible trate su variable como un booleano y
no como una cadena.
A partir de Ansible Core 2.12, los condicionales when siempre tratan las cadenas
como booleanos true si incluyen algún contenido. (El entorno de ejecución de
automatización predeterminado en Ansible Automation Platform 2.2 usa Ansible
Core 2.13).
Por lo tanto, si la variable run_my_task en el ejemplo anterior se escribiera como
se muestra en el siguiente ejemplo, se trataría como una cadena con contenido y
tendría el valor booleano true, y la tarea se ejecutaría. Probablemente este no sea
el comportamiento que desea.
  run_my_task: "false"
Sin embargo, si se hubiera escrito como se muestra en el siguiente ejemplo, se
trataría como el valor booleano false y la tarea no se ejecutaría:
  run_my_task: false
Para asegurarse de que este sea el caso, puede reescribir la condición when
anterior para convertir un valor de cadena accidental en un booleano y pasar valores
booleanos sin cambios:
      when: run_my_task | bool

Importante
Observe la sangría de la declaración when. Debido a que la declaración when no es
una variable de módulo, se la debe colocar fuera del módulo con sangría en el nivel
superior de la tarea.
Una tarea es un diccionario YAML, y la declaración when es simplemente una clave
más en la tarea, como el nombre de la tarea y el módulo que usa. Una convención
común coloca cualquier palabra clave when que pueda estar presente después del
nombre de la tarea y del módulo (y los argumentos del módulo).
Realización de pruebas de varias condiciones
Una declaración when se puede usar para evaluar condicionales múltiples. Para ello, los
condicionales se pueden combinar con las palabras clave and u or y se pueden agrupar con
paréntesis.
En los siguientes fragmentos, se muestran algunos ejemplos de cómo expresar condiciones
múltiples.
• Si una declaración condicional se debe cumplir cuando ambas condiciones son verdaderas,
debe usar la declaración or. Por ejemplo, la siguiente condición se cumple si la máquina ejecuta
Red Hat Enterprise Linux o Fedora:
when: ansible_facts['distribution'] == "RedHat" or ansible_facts['distribution']
 == "Fedora"
• Con la operación and, ambas condiciones deben ser verdaderas para que se cumpla con toda
la declaración condicional. Por ejemplo, la siguiente condición se cumple si el host remoto es un
host Red Hat Enterprise Linux 9.0 y el kernel instalado es la versión especificada:
when: ansible_facts['distribution_version'] == "9.0" and ansible_facts['kernel']
 == "5.14.0-70.13.1.el9_0.x86_64"

La palabra clave when también soporta el uso de una lista para describir una lista de
condiciones. Cuando se proporciona una lista a la palabra clave when, todos los condicionales se
combinan usando la operación and. En el siguiente ejemplo, se muestra otra forma de combinar
varias declaraciones condicionales usando el operador and:
when:
  - ansible_facts['distribution_version'] == "9.0"
  - ansible_facts['kernel'] == "5.14.0-70.13.1.el9_0.x86_64"
Este formato mejora la legibilidad, un objetivo clave de los playbooks de Ansible bien escritos.
• Puede expresar declaraciones condicionales más complejas agrupando las condiciones con
paréntesis. Esto asegura que se interpreten correctamente.
Por ejemplo, la siguiente declaración condicional se cumple si la máquina ejecuta Red Hat
Enterprise Linux 9 o Fedora 34. Este ejemplo usa el carácter mayor que (>) para que el
condicional largo se pueda dividir en varias líneas en el playbook, a fin de que sea más fácil de
leer.
when: >
    ( ansible_facts['distribution'] == "RedHat" and
      ansible_facts['distribution_major_version'] == "9" )
    or
    ( ansible_facts['distribution'] == "Fedora" and
    ansible_facts['distribution_major_version'] == "34" )
Combinación de bucles y tareas condicionales
Puede combinar los bucles y los condicionales.
En el siguiente ejemplo, el módulo ansible.builtin.dnf se instala en el paquete mariadb-
server si hay un sistema de archivos montado en / con más de 300 MiB libres. El dato
ansible_facts['mounts'] es una lista de diccionarios, cada uno de los cuales representa
información acerca de un sistema de archivos instalado. El bucle realiza la iteración de cada
diccionario en la lista, y la declaración condicional no se cumple, a menos que se determine que
un diccionario representa un sistema de archivos montado en donde ambas condiciones son
verdaderas.
- name: install mariadb-server if enough space on root
  ansible.builtin.dnf:
    name: mariadb-server
    state: latest
  loop: "{{ ansible_facts['mounts'] }}"
  when: item['mount'] == "/" and item['size_available'] > 300000000
Importante
Cuando usa when con loop para una tarea, se verifica la declaración when de cada
ítem.

Implementación de manejadores
Objetivos
• Implementar una tarea que se ejecute solo cuando otra tarea cambie el host gestionado.
Manejadores de Ansible
Los módulos Ansible están diseñados para ser idempotentes. Esto significa que, si ejecuta un
playbook varias veces, el resultado es siempre el mismo. Puede ejecutar plays y sus tareas varias
veces, pero los hosts gestionados solo se modifican si esos cambios son necesarios para que los
hosts gestionados alcancen el estado deseado.
No obstante, algunas veces, cuando una tarea realiza un cambio en el sistema, se puede tener
que ejecutar otra tarea. Por ejemplo, un cambio en un archivo de configuración del servicio puede
luego requerir que el servicio se vuelva a cargar para que se aplique la configuración modificada.
Los manejadores son tareas que responden a una notificación desencadenada por otras tareas.
Las tareas solo notifican a sus manejadores cuando la tarea cambia algo en un host gestionado.
Cada controlador se activa por su nombre después del bloque de tareas del play.
Si ninguna tarea notifica al manejador por nombre, no se ejecutará el manejador. Si una o más
tareas notifican al manejador, este se ejecutará exactamente una vez después de que todas
las demás tareas en el play se hayan completado. Debido a que los manejadores son tareas, los
administradores pueden usar los mismos módulos en manejadores que usarían para cualquier otra
tarea.
Generalmente, los manejadores se usan para reiniciar los hosts y los servicios.
Importante
Siempre use nombres únicos para sus manejadores. Es posible que tenga resultados
inesperados si más de un manejador usa el mismo nombre.
Los manejadores se pueden considerar como tareas inactive que solo se desencadenan cuando se
las invoca explícitamente mediante una declaración notify. En el siguiente fragmento se muestra
cómo el servidor Apache solo se reinicia mediante el manejador restart apache cuando un
archivo de configuración se actualiza y lo notifica:
tasks:
  - name: copy demo.example.conf configuration template
    ansible.builtin.template:
      src: /var/lib/templates/demo.example.conf.template
      dest: /etc/httpd/conf.d/demo.example.conf
    notify:
      - restart apache
handlers:
  - name: restart apache

Descripción de los beneficios del uso de manejadores
Como analizamos en la documentación Ansible, debemos recordar algunos aspectos importantes
acerca del uso de manejadores:
• Los manejadores se ejecutan siempre en el orden especificado por la sección handlers del
play. No se ejecutan en el orden en que aparecen en la lista por la declaración notify en una
tarea ni en el orden en que las tareas los notifican.
• Los manejadores se ejecutan después de que se hayan completado todas las demás tareas en
el play. Un manejador invocado por una tarea en la parte tasks del playbook no se ejecutará
hasta que se hayan procesado todas las tareas en tasks. (Hay algunas excepciones menores a
esto).

Manejo de fallas de tareas
Objetivos
• Controlar lo que sucede cuando falla una tarea y qué condiciones hacen que falle una tarea.
Gestión de errores de tareas en plays
Ansible evalúa los códigos de retorno de cada tarea para determinar si una tarea se realizó
satisfactoriamente o con errores. Generalmente, cuando una tarea falla, Ansible omite
inmediatamente todas las tareas posteriores.
No obstante, algunas veces puede desear continuar la ejecución del play, aunque una tarea falle.
Por ejemplo, puede esperar que una tarea específica falle y tal vez desee recuperarla ejecutando
otra tarea de forma condicional. Pueden usarse varias características de Ansible para gestionar los
errores de tareas.
Fallas de tareas ignoradas
De forma predeterminada, si una tarea falla, se cancela el play. Sin embargo, el comportamiento
puede anularse si se ignoran las tareas fallidas. Puede usar la palabra clave ignore_errors en
una tarea para lograr esto.
En el siguiente fragmento, se muestra cómo usar ignore_errors en una tarea para continuar la
ejecución de un playbook en el host, aun si la tarea falla. Por ejemplo, si el paquete notapkg no
existe, el módulo ansible.builtin.dnf falla, pero si se tiene ignore_errors establecido
como true, la ejecución continuará.
- name: Latest version of notapkg is installed
  ansible.builtin.dnf:
    name: notapkg
    state: latest
  ignore_errors: true
Forzado de la ejecución de manejadores después de la falla de
una tarea
En general, cuando falla una tarea y se cancela el play en ese host, no se ejecutan los manejadores
informados por las tareas anteriores en el play. Si establece la palabra clave force_handlers:
true en el play, se llama a los manejadores notificados incluso si se canceló el play porque falló
una tarea posterior.
Importante
Si ha establecido ignore_errors: true en una tarea o para el play de la tarea,
si esa tarea falla, se ignora la falla. En ese caso, el play continúa ejecutándose y los
manejadores aún se ejecutan, incluso si ha establecido force_handlers: false,
a menos que algún otro error haga que el play falle.

Bloques Ansible y control de errores
En los playbooks, los blocks (bloques) son cláusulas que agrupan tareas de forma lógica y se
pueden usar para controlar cómo se ejecutan las tareas. Por ejemplo, un bloque de tareas puede
tener una palabra clave when para aplicar un condicional a varias tareas:
- name: block example
  hosts: all
  tasks:
    - name: installing and configuring DNF versionlock plugin
      block:
      - name: package needed by dnf
        ansible.builtin.dnf:
          name: python3-dnf-plugin-versionlock
          state: present
      - name: lock version of tzdata
        ansible.builtin.lineinfile:
          dest: /etc/yum/pluginconf.d/versionlock.list
          line: tzdata-2016j-1
          state: present
      when: ansible_distribution == "RedHat"
Los bloques también permiten el control de errores junto con los enunciados rescue y always. Si
falla alguna de las tareas de block, se ejecutan las tareas rescue para recuperarse.
Después de que se ejecuten las tareas en la cláusula block, así como las tareas en la cláusula
rescue si hubo una falla, se ejecutan las tareas en la cláusula always.
Para resumir:
• block: define las tareas principales para ejecutar.
• rescue: define las tareas que se ejecutarán si fallan las tareas definidas en la cláusula block.
• always: define las tareas que se ejecutarán siempre, independientemente del éxito o de la falla
de las tareas definidas en las cláusulas block y rescue.
En el siguiente ejemplo, se muestra cómo implementar un bloque en un playbook.
  tasks:
    - name: Upgrade DB
      block:
        - name: upgrade the database
          ansible.builtin.shell:
            cmd: /usr/local/lib/upgrade-database
      rescue:
        - name: revert the database upgrade
          ansible.builtin.shell:
            cmd: /usr/local/lib/revert-database
      always:
        - name: always restart the database

Resumen
• Los bucles se usan para iterar un conjunto de valores, como una simple lista de cadenas o una
lista de diccionarios.
• Los condicionales se pueden usar para ejecutar tareas o plays únicamente cuando se hayan
cumplido ciertas condiciones.
• Los manejadores son tareas especiales que se ejecutan al final de un play si otras tareas los
notifican.
• Los manejadores solo son notificados cuando una tarea informa que se cambió algo en un host
gestionado.
• Las tareas se pueden configurar para manejar condiciones de error ignorando una falla en las
tareas, forzando a los manejadores a ser invocados aun cuando la tarea haya fallado, marcar una
tarea como con errores cuando fue satisfactoria o reemplazar el comportamiento que hace que
la tarea se marque como modificada.
• Los bloques se usan para agrupar tareas como una unidad y ejecutar otras tareas dependiendo
de si todas las tareas en el bloque se realizaron satisfactoriamente.

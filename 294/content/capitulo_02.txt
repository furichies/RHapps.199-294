Compilación de un inventario de Ansible
Objetivos
• Describir los conceptos de inventario de Ansible y administrar un archivo de inventario estático.
Definición de inventario
Un inventario define un conjunto de hosts que gestiona Ansible. Estos hosts también pueden ser
asignados a grupos, que pueden ser gestionados colectivamente. Los grupos pueden contener
grupos secundarios, y los hosts pueden ser miembros de múltiples grupos. El inventario también
puede establecer variables que se apliquen a los hosts y grupos que define.
Existen dos formas de definir los inventarios de host. Use un archivo de texto para definir un
inventario de host estático. Use un complemento de Ansible para generar un inventario de host
dinámico según sea necesario, usando proveedores de información externos.
Especificación de hosts gestionados con un inventario
estático
Un archivo de inventario estático es un archivo de texto que especifica los hosts gestionados a
los que apunta Ansible. Puede escribir este archivo usando varios formatos diferentes, incluido un
estilo INI o YAML. El formato estilo INI es muy común y se usa para la mayoría de los ejemplos en
este curso.
nota
Ansible soporta múltiples formatos de inventario estático. Esta sección se centra en
el más frecuente, el formato estilo INI.
En su forma más simple, un archivo de inventario estático estilo INI es una lista de nombres de host
o direcciones IP de hosts gestionados, cada uno en una línea única:
web1.example.com
web2.example.com
db1.example.com
db2.example.com
192.0.2.42
Sin embargo, normalmente organiza hosts gestionados en grupos de hosts. Los grupos de hosts le
permiten ejecutar Ansible de manera más efectiva en comparación con un conjunto de sistemas.
En este caso, cada sección comienza con un nombre de grupo de hosts encerrado entre corchetes
([]). A continuación, siguen el nombre de host o una dirección IP para cada host gestionado en el
grupo, cada uno en una línea única.
En el siguiente ejemplo, el inventario del host define dos grupos de hosts: webservers y db-
servers.

Definición de grupos anidados
Los inventarios de host de Ansible pueden incluir grupos de grupos de hosts. Esto se logra
creando un nombre de grupo de host con el sufijo :children. En el siguiente ejemplo, se crea
un nuevo grupo, denominado north-america, que incluye todos los hosts de los grupos usa y
canada.
[usa]
washington1.example.com
washington2.example.com
[canada]
ontario01.example.com
ontario02.example.com
[north-america:children]
canada
usa
Un grupo puede tener hosts gestionados y grupos secundarios como miembros. Por ejemplo, en
el inventario anterior, podría agregar una sección [north-america] que tenga su propia lista de
hosts gestionados. Esta lista de hosts se fusionaría con los hosts adicionales que hereda el grupo
north-america de sus grupos secundarios.
Simplificación de las especificaciones de hosts con rangos
Puede especificar rangos en los nombres de hosts o direcciones IP para simplificar inventarios de
hosts de Ansible. Puede especificar rangos numéricos o alfabéticos. Los rangos tienen la siguiente
sintaxis:
[START:END]
Los rangos hacen coincidir todos los valores desde START hasta END, inclusive. Considere los
siguientes ejemplos:
• 192.168.[4:7].[0:255] coincide con todas las direcciones IPv4 en la red 192.168.4.0/22 (de
192.168.4.0 a 192.168.7.255).
• server[01:20].example.com coincide con todos los hosts denominados
server01.example.com a server20.example.com.
• [a:c].dns.example.com coincide con los hosts denominados a.dns.example.com,
b.dns.example.com y c.dns.example.com.
• 2001:db8::[a:f] coincide con todas las direcciones IPv6 de 2001:db8::a a 2001:db8::f.
Si se incluyen ceros a la izquierda en rangos numéricos, se usan en el patrón. El segundo ejemplo
anterior no coincide con server1.example.com, pero sí con server07.example.com.
Verificación del inventario
Puede usar el comando ansible-navigator inventory para consultar un archivo de
inventario. Puede hacer esto para verificar la presencia de un host o un grupo en el inventario.

Importante
Si el inventario contiene un host y un grupo de hosts con el mismo nombre, el
comando ansible-navigator inventory imprime una advertencia.
Asegúrese de que los grupos de hosts no usen los mismos nombres que los hosts en
el inventario.
Reemplazo de la ubicación del inventario
El archivo /etc/ansible/hosts se considera el archivo de inventario estático predeterminado
del sistema. Sin embargo, la práctica habitual es no usar ese archivo, sino especificar una
ubicación diferente para los archivos de inventario.
Los comandos ansible-navigator que usa para ejecutar playbooks pueden especificar la
ubicación de un archivo de inventario en la línea de comandos con la opción --inventory
PATHNAME o -i PATHNAME, donde PATHNAME es la ruta al archivo de inventario deseado.
nota
También puede definir una ubicación predeterminada diferente para el archivo de
inventario en su archivo de configuración de Ansible.
Inventarios dinámicos
La información de inventario de Ansible también puede generarse de forma dinámica con la
información provista por bases de datos externas. La comunidad de código abierto ha escrito
varios complementos (plug-ins) de inventario dinámicos que están disponibles desde el proyecto
upstream de Ansible. Si estos complementos (plug-ins) Ansible no satisfacen sus necesidades,
también puede escribir sus propios.
Por ejemplo, un programa de inventario dinámico podría contactarse con su servidor de Red Hat
Satellite o su cuenta de Amazon EC2, y usar la información almacenada allí para construir un
inventario de Ansible. Dado que el programa hace esto cuando ejecuta Ansible, puede completar
el inventario con información actualizada provista por el servicio a medida que se agregan nuevos
hosts y se eliminan hosts anteriores.
Cómo usar un inventario dinámico está fuera del alcance de esta sección.

Administración de archivos de
configuración de Ansible
Objetivos
• Describir dónde se encuentran los archivos de configuración de Ansible, cómo los selecciona
Ansible y editarlos para aplicar los cambios a la configuración predeterminada.
Configuración de Ansible
Puede crear y editar dos archivos en cada uno de los directorios de su proyecto Ansible que
configuran el comportamiento de Ansible y el comando ansible-navigator. Un directorio de
proyectos de Ansible es un directorio desde el cual ejecuta sus playbooks mediante el comando
ansible-navigator.
• ansible.cfg, que configura el comportamiento de varias herramientas de Ansible.
• ansible-navigator.yml, que cambia las opciones predeterminadas para el comando
ansible-navigator.
Gestión de la configuración de Ansible
Cree un archivo de configuración ansible.cfg en cada uno de sus directorios de proyectos de
Ansible. El archivo de configuración de Ansible consiste en varias secciones; cada sección contiene
parámetros definidos como pares de clave-valor. Los títulos de las secciones se incluyen entre
paréntesis. Para la operación básica, use las siguientes dos secciones:
• [defaults], que establece valores predeterminados para la operación de Ansible
• [privilege_escalation], que configura el modo en que Ansible realiza el aumento de
privilegios en hosts gestionados
El siguiente es un archivo ansible.cfg de muestra:
[defaults]
inventory = ./inventory 
remote_user = user 
ask_pass = false 
[privilege_escalation]
become = true 
become_method = sudo 
become_user = root 
become_ask_pass = false 
El parámetro inventory especifica la ruta a un archivo de inventario estático o a un
directorio que contenga múltiples archivos de inventario estático y scripts de inventario
dinámico.

conectarse a los hosts gestionados. En un entorno de ejecución de automatización

El parámetro ask_pass especifica si se debe solicitar o no una contraseña SSH. Establece

El parámetro become especifica si se debe cambiar automáticamente el usuario en el host
gestionado (por lo general, a root) después de la conexión. Establece false de forma
predeterminada. Si bien puede establecer este parámetro en true para habilitar el aumento
de privilegios para todos los plays, puede decidir habilitar el aumento de privilegios solo en
los plays, bloques o tareas que requieren privilegios elevados.
El parámetro become_method especifica cómo cambiar de usuario. El valor predeterminado
es sudo, aunque hay otros métodos disponibles, como su.
El parámetro become_user especifica a qué usuario cambiar en el host gestionado.
Establece root de forma predeterminada.
El parámetro become_ask_pass especifica si se debe solicitar o no una contraseña para
el parámetro become_method. Establece false de forma predeterminada. Si usa el
comando ansible-navigator, establecer este parámetro en true requiere deshabilitar
los artefactos del playbook y usar el modo de salida estándar.
Importante
El comando ansible-playbook también puede usar un archivo .ansible.cfg
en su directorio de inicio o el archivo /etc/ansible/ansible.cfg, pero el
comando ansible-navigator no usa estos archivos locales en su sistema.
Escalación de privilegios
Algunas tareas, como la instalación de software, solo pueden completarse si el usuario tiene
privilegios elevados. Si sus playbooks se conectan a su host gestionado como un usuario regular,
debe habilitar el aumento de privilegios para que esas tareas se realicen correctamente.
En Red Hat Enterprise Linux 8 y 9, la configuración predeterminada del archivo /etc/sudoers
garantiza que todos los usuarios en el grupo wheel tengan la capacidad de usar sudo para
convertirse en root después de ingresar su contraseña.
Si su archivo de configuración de Ansible usa el parámetro become_method = sudo, puede
usar el archivo /etc/sudoers como ejemplo para otorgar acceso sudo a usuarios o grupos
adicionales. Cree un archivo en el directorio /etc/sudoers.d y asegúrese de que el archivo sea
propiedad de root.
Las siguientes líneas de un archivo /etc/sudoers muestran que se requiere y no se requiere una
contraseña:
## Allows people in group wheel to run all commands
%wheel  ALL=(ALL)       ALL
## Same thing without a password
# %wheel        ALL=(ALL)       NOPASSWD: ALL

Puede crear un archivo de configuración (o archivo de ajustes) para ansible-navigator para

puede estar en formato JSON (.json) o YAML (.yml o .yaml). Esta discusión se centra en el

El navegador de contenido de automatización busca un archivo de configuración en el siguiente
orden y usa el primer archivo que encuentra:
• Si se establece la variable de entorno ANSIBLE_NAVIGATOR_CONFIG, use el archivo de
configuración en la ubicación que especifica.
• Un archivo ansible-navigator.yml en su directorio de proyecto actual de Ansible.
• Un archivo .ansible-navigator.yml en su directorio de inicio (observe que el nombre del
archivo contiene un punto al comienzo del nombre).
Al igual que el archivo de configuración de Ansible, cada proyecto puede tener su propio archivo
de configuración del navegador de contenido de automatización.
El siguiente archivo ansible-navigator.yml configura algunos ajustes comunes:
---
ansible-navigator:
  execution-environment: 
    image: utility.lab.example.com/ee-supported-rhel8:latest 
    pull:
      policy: missing 
  playbook-artifact: 
    enable: false 
  mode: stdout 
La sección execution-environment configura los ajustes para el entorno de ejecución de
automatización que usa el comando ansible-navigator.
La clave image define el nombre de la imagen del contenedor que se usará para el entorno
de ejecución de automatización.
La clave policy anidada debajo de la sección pull indica que solo se extraiga la imagen del
contenedor si aún no existe en la máquina local.
La sección playbook-artifact configura los ajustes para los archivos JSON que Ansible
genera cada vez que ejecuta un playbook. Cada archivo JSON generado registra información
sobre la ejecución de un playbook específico. Puede usar estos archivos para revisar los
resultados de la ejecución de un playbook o para solucionar problemas del playbook.
La clave enable anidada debajo de la sección playbook-artifact deshabilita la
generación de artefactos de playbook cuando se usa el comando ansible-navigator
run. Los artefactos del playbook se deben deshabilitar cuando se le solicite una contraseña
al ejecutar un playbook. Puede anular temporalmente esta configuración desde la línea de
comandos con la opción --pae.
La clave mode define el modo de salida para el comando ansible-navigator. El valor para
esta clave debe establecerse en interactive (predeterminado) o stdout. Puede anular
temporalmente esta configuración desde la línea de comandos con la opción -m.

Escritura y ejecución de playbooks
Objetivos
• Escribir un playbook de Ansible básico y ejecutarlo con el navegador de contenido de
automatización.
Playbooks de Ansible
El poder de Ansible es que puede usar playbooks para ejecutar varias tareas complejas respecto
de un conjunto de hosts de destino de una manera fácilmente repetible.
Una tarea es la aplicación de un módulo para realizar una unidad específica de trabajo. Un play
es una secuencia de tareas que se aplicarán, en orden, a uno o más hosts seleccionados de su
inventario. Un playbook es un archivo de texto que contiene una lista de uno o más plays para
ejecutar en un orden específico.
Los plays le permiten modificar un conjunto complejo y extenso de tareas administrativas
manuales en una rutina fácilmente repetible con resultados predecibles y satisfactorios. En
un playbook, puede guardar la secuencia de tareas en un play de una forma inmediatamente
ejecutable y legible por el ojo humano. Las tareas en sí, debido a la manera en la que se escriben,
documentan los pasos necesarios para implementar su aplicación o infraestructura.
Formato de un playbook de Ansible
El siguiente ejemplo contiene un play con una sola tarea.
---
- name: Configure important user consistently
  hosts: servera.lab.example.com
  tasks:
    - name: Newbie exists with UID 4000
      ansible.builtin.user:
        name: newbie
        uid: 4000
        state: present
Un playbook es un archivo de texto escrito en formato YAML y se guarda generalmente con la
extensión .yml. El playbook usa sangría con caracteres de espacio para indicar la estructura de
sus datos. YAML no establece requisitos estrictos sobre cuántos espacios se usan para la sangría,
pero se aplican dos reglas básicas.
• Los elementos de datos en el mismo nivel en la jerarquía (como ítems en la misma lista) deben
tener la misma sangría.
• Los ítems que son elementos secundarios de otro ítem deben tener más sangría que sus
elementos principales.
También puede agregar líneas en blanco para la capacidad de lectura.

El playbook comienza con una línea que consiste en tres guiones (---) para marcar el inicio
de documento. También puede finalizar con tres puntos (...) como para indicar el fin del
documento, si bien en la práctica por lo general se omite.
Entre estos marcadores, el playbook se define como una lista de plays. Un ítem en una lista YAML
comienza con un solo guion seguido de un espacio. Por ejemplo, una lista YAML puede verse de la
siguiente manera:
- apple
- orange
- grape
En el ejemplo del playbook anterior, la línea después de --- comienza con un guion e inicia el
primer (y único) play en la lista de plays.
Cada play en sí es una recopilación de pares de clave-valor. Las claves en el mismo play deben
tener la misma sangría. En el siguiente ejemplo se muestra un fragmento de código YAML con
tres claves. Las primeras dos claves tienen valores simples. La tercera tiene una lista de tres ítems
como valor.
  name: just an example
  hosts: webservers
  tasks:
    - first
    - second
    - third
El play de ejemplo inicial tiene tres claves: name, hosts y tasks. Todas estas claves tienen la
misma sangría.
La primera línea del play de ejemplo comienza con un guion y un espacio (que indican que el
play es el primer ítem de una lista); luego, sigue la primera clave, name. La clave name asocia una

La segunda clave en el play es una clave hosts, que especifica los hosts respecto de los cuales se

módulo (name, uid y state).

Implementación de varios plays
Objetivos
• Escribir un playbook que use múltiples plays con aumento de privilegios por play y aprovechar
eficazmente el navegador de contenido de automatización para encontrar nuevos módulos en
Ansible Content Collections disponibles a fin de implementar tareas para un play.
Escritura de varios plays
Un playbook es un archivo YAML que contiene una lista de uno o más plays. Recuerde que un solo
play es una lista ordenada de tareas para ejecutar respecto de hosts seleccionados del inventario.
Por lo tanto, si un playbook contiene varios plays, cada play podría aplicar sus tareas a un conjunto
de hosts diferente.
Esto puede ser muy útil cuando se organiza una implementación compleja que puede involucrar
diferentes tareas en diferentes hosts. Puede escribir un playbook que ejecute un play respecto de
un conjunto de hosts y que, cuando este finaliza, ejecute otro play respecto de otro conjunto de
hosts.
Escribir un playbook que contenga varios plays es muy sencillo. Cada play en el playbook se
escribe como un ítem de lista de nivel superior en el playbook. Cada play es un ítem de una lista
que contiene las palabras clave de plays habituales.
En el siguiente ejemplo se muestra un playbook simple con dos plays. El primer play se ejecuta
respecto de web.example.com y el segunda, respecto de database.example.com.
---
# This is a simple playbook with two plays
- name: First play
  hosts: web.example.com
  tasks:
    - name: First task
      ansible.builtin.dnf:
        name: httpd
        state: present
    - name: Second task
      ansible.builtin.service:
        name: httpd
        enabled: true
- name: Second play
  hosts: database.example.com
  tasks:

Usuarios remotos y aumento de privilegios en los plays
Los plays pueden usar usuarios remotos o parámetros de aumento de privilegios diferentes a
aquellos especificados por los valores predeterminados en el archivo de configuración. Puede
anular esta configuración en el play en sí en el mismo nivel que las palabras clave hosts o tasks.
Atributos de usuario
Las tareas en playbooks se ejecutan generalmente a través de una conexión de red en los hosts
gestionados. Ansible tiene que conectarse a cada host gestionado como algún usuario para
ejecutar esas tareas.
De forma predeterminada, si usa ansible-navigator run para ejecutar un playbook, Ansible
se conecta al host gestionado como el usuario actual dentro del entorno de ejecución de la
automatización, root.
nota
Si ejecuta un comando de Ansible que no usa entornos de ejecución, como
ansible-playbook, Ansible intentará de forma predeterminada autenticarse
en el host gestionado remoto con el nombre de usuario de la cuenta que usó para
ejecutar el comando.
Puede establecer una directiva remote_user en el archivo ansible.cfg de su proyecto para
configurar Ansible para usar una cuenta de usuario diferente en los hosts gestionados cuando
inicie sesión inicialmente. Si aún necesita que las tareas se ejecuten como root, puede usar el
aumento de privilegios para cambiar a ese usuario después de la conexión remota inicial.
Sin embargo, también puede especificar el usuario remoto que Ansible usa para cada play.
Si el usuario remoto definido en la configuración Ansible para la ejecución de las tareas no es
adecuado, se lo puede sobrescribir usando la palabra clave remote_user dentro de un play.
remote_user: remoteuser
Importante
Ansible determina qué cuenta de usuario usar cuando se conecta a un host
gestionado según la siguiente lista, seleccionando el primer nombre de usuario que
encuentra en este orden:
• La variable ansible_user establecida para el host o el grupo, si está
configurada.
• El remote_user del play actual, si está configurado.
• El remote_user del archivo de configuración ansible.cfg, si está
configurado.
Si no se ha establecido ningún valor para ninguna de las configuraciones anteriores
y está ejecutando playbooks usando ansible-navigator con un entorno de
ejecución, Ansible usa root. (Si usa ansible-playbook, Ansible usa el nombre
del usuario que ejecutó el comando).

Atributos de aumento de privilegios
También puede configurar el aumento de privilegios en un play. Use la palabra clave booleana
become para habilitar o deshabilitar el aumento de privilegios para un play o tarea individual. Esto
anula la configuración en el archivo de configuración ansible.cfg. Puede seleccionar yes o
true para habilitar el aumento de privilegios, o no o false para deshabilitarlo.
become: true
Si se habilita el aumento de privilegios, use la palabra clave become_method en el play para
especificar el método de aumento de privilegios para usar para ese play. El siguiente ejemplo
especifica que se use sudo como el método de aumento de privilegios.
become_method: sudo
Asimismo, con el aumento de privilegios habilitado, puede usar la palabra clave become_user en
el play para definir la cuenta del usuario que debe usarse para el aumento de privilegios en ese
play específico.
become_user: privileged_user
En el siguiente ejemplo se demuestran algunas de estas palabras clave en un play:
- name: /etc/hosts is up-to-date
  hosts: datacenter-west
  remote_user: automation
  become: true

A diferencia de la mayoría de los módulos, ansible.builtin.command no es idempotente.
Cada vez que se especifica la tarea en un play, se ejecuta e informa que cambió algo en el host
gestionado, incluso si no es necesario cambiar nada.
Puede intentar que la tarea sea más segura configurándola para que se ejecute solo en función
de la existencia de un archivo. La opción creates hace que la tarea se ejecute solo si falta un
archivo; la suposición es que si la tarea se ejecuta, crea ese archivo. La opción removes hace que
la tarea se ejecute solo si hay un archivo; la suposición es que, si la tarea se ejecuta, elimina ese
archivo.
Por ejemplo, la siguiente tarea solo se ejecuta si /opt/db/database.db no está presente:
- name: Initialize the database
  ansible.builtin.command:
    cmd: /opt/bin/makedb.sh
    creates: /opt/db/database.db
El módulo ansible.builtin.command no puede acceder a las variables del entorno de la
shell ni realizar operaciones de la shell, como redirección de entrada/salida o pipelines. Cuando
necesite realizar un procesamiento de shell, puede usar el módulo ansible.builtin.shell.
Al igual que el módulo ansible.builtin.command, pase los comandos que se deben ejecutar
como argumentos al módulo.
Ambos módulos ansible.builtin.command y ansible.builtin.shell requieren una
instalación Python de trabajo en el host gestionado. Un tercer módulo, ansible.builtin.raw,
puede ejecutar comandos directamente con la shell remota y eludir el subsistema del módulo.
Esto es útil cuando administra sistemas que no pueden tener Python instalado (por ejemplo, un
enrutador de red). También puede usarse para instalar Python en un host gestionado.
Importante
De ser posible, intente evitar los módulos ansible.builtin.command,
ansible.builtin.shell y ansible.builtin.raw en los playbooks, por más
simple que parezca su uso. Debido a que estos adoptan comandos arbitrarios en los
hosts gestionados, es muy fácil programar playbooks no idempotentes con estos
módulos.
Si no necesita usarlos, probablemente sea mejor usar el módulo
ansible.builtin.command primero, y recurrir a los módulos
ansible.builtin.shell o ansible.builtin.raw solo si necesita sus
características especiales.
Otro ejemplo sería la siguiente tarea que usa el módulo ansible.builtin.shell que no es
idempotente. Cada vez que se ejecuta el play, reescribe /etc/resolv.conf aunque ya conste
de la línea nameserver 192.0.2.1. Una tarea que no es idempotente muestra el estado
changed cada vez que se ejecuta la tarea.
- name: Non-idempotent approach with shell module
  ansible.builtin.shell:
    cmd: echo "nameserver 192.0.2.1" > /etc/resolv.conf

Abreviatura de playbook obsoleto
Algunos playbooks pueden usar un método de abreviatura anterior para definir tareas y ponen
los pares de clave-valor para el módulo en la misma línea que el nombre del módulo. Por ejemplo,
puede ver esta sintaxis:
  tasks:
    - name: Shorthand form
      ansible.builtin.service: name=httpd enabled=true state=started
En general, escribiría la misma tarea de la siguiente manera:
  tasks:
    - name: Normal form
      ansible.builtin.service:
        name: httpd
        enabled: true
        state: started
En general, debe evitar la forma de abreviatura y usar la forma normal.
La forma normal tiene más líneas, pero es más fácil para trabajar. Las palabras clave de la tarea se
apilan verticalmente y son más fáciles de diferenciar. Sus ojos pueden recorrer el play hacia abajo
con menos movimiento de izquierda a derecha, facilitando la lectura.
Además, la sintaxis normal es YAML nativa, mientras que la abreviatura no lo es. Las herramientas
de resaltado de sintaxis en editores de texto pueden ayudarlo de manera más efectiva si usa el
formato normal en lugar del formato abreviado.
Puede encontrar esta sintaxis en documentación y playbooks anteriores de otras personas y la
sintaxis aún funciona.

capítulo 2 |  Implementación de un playbook de Ansible
Resumen
• Un play es una lista ordenada de tareas que se ejecutan respecto de hosts seleccionados del
inventario.
• Un playbook es un archivo de texto que contiene una lista de uno o más plays para ejecutar en
orden.
• Los playbooks de Ansible se escriben en formato YAML.
• Los plays de Ansible son idempotentes, lo que significa que evitan realizar cambios si detectan
que el estado actual coincide con el estado final deseado.
• Los archivos YAML están estructurados mediante la sangría de espacio para representar la
jerarquía de datos.
• Las tareas se implementan mediante el código estandarizado incluido como módulos Ansible.
• Los módulos de Ansible se empaquetan en Ansible Content Collections, que son un formato
de distribución para el contenido de Ansible que puede incluir playbooks, roles, módulos y
complementos (plug-ins).
• El comando ansible-navigator doc puede enumerar módulos en sus entornos de
ejecución de automatización y brindar documentación y fragmentos de códigos a modo de
ejemplo de cómo usarlos en playbooks.
• El comando ansible-navigator run se usa para ejecutar playbooks y validar la sintaxis del
playbook.

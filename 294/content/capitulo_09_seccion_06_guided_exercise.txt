Ejercicio Guiado
Administración del proceso de arranque y
procesos programados
Gestionar el proceso de inicio, programar trabajos recurrentes y reiniciar los hosts
gestionados.
Resultados
• Programar un trabajo Cron.
• Eliminar un solo trabajo específico de Cron de un archivo crontab.
• Programar una tarea de at.
• Establecer el destino de arranque predeterminado en los hosts gestionados.
• Reiniciar los hosts gestionados.
Antes De Comenzar
Con el usuario student en la máquina workstation, use el comando lab para preparar su
sistema para este ejercicio.
Este comando prepara su entorno y garantiza que estén disponibles todos los recursos
requeridos, incluido el directorio del proyecto /home/student/system-process.
[student@workstation ~]$ lab start system-process
Instrucciones
 1.
Cambie al directorio /home/student/system-process.
[student@workstation ~]$ cd ~/system-process
[student@workstation system-process]$
 2.
Cree el playbook create_crontab_file.yml en el directorio de trabajo.
Configure el playbook para usar el módulo ansible.builtin.cron para crear un
archivo crontab denominado /etc/cron.d/add-date-time que programa un trabajo
cron recurrente. El trabajo debe ejecutarse con el usuario devops cada dos minutos
comenzando a las 09:00 y terminando a las 16:59 de lunes a viernes. El trabajo debe
adjuntar la fecha y hora del archivo /home/devops/my_datetime_cron_job.
2.1.
Cree el playbook create_crontab_file.yml y agregue las líneas necesarias
para iniciar el play. Debe apuntar a los hosts gestionados del grupo webservers y
habilitar el aumento de privilegios.

Defina una tarea que use el módulo ansible.builtin.cron para

nota
El módulo ansible.builtin.cron proporciona una opción name para describir
de forma única la entrada del archivo crontab y garantizar los resultados
esperados.
El valor que usa para la opción name se agrega al archivo crontab como
comentario. Por ejemplo, se requiere la opción name si elimina una entrada de
crontab usando state: absent.
Además, la opción name evita que se cree siempre una nueva entrada de crontab
cuando se configura el estado predeterminado, state: present.
  tasks:
    - name: Crontab file exists
      ansible.builtin.cron:
        name: Add date and time to a file
        job: date >> /home/devops/my_date_time_cron_job
2.3.
Configure el trabajo para que se ejecute cada dos minutos comenzando a las 09:00 y
finalizando a las 16:59 de lunes a viernes.
        minute: "*/2"
        hour: 9-16
        weekday: 1-5
2.4.
Use el parámetro cron_file para usar el archivo crontab denominado /etc/
cron.d/add-date-time en lugar del crontab de un usuario individual en /var/
spool/cron/.
Una ruta relativa colocará el archivo en el directorio /etc/cron.d.
Si se usa el parámetro cron_file, también debe especificar el parámetro user para
el archivo del sistema crontab. Use el usuario devops para este trabajo.
        user: devops
        cron_file: add-date-time
        state: present
2.5.
Cuando se complete, el playbook debe verse de la siguiente forma. Revise el
playbook para comprobar la precisión.

 4.
Cree el playbook schedule_at_task.yml en el directorio de trabajo. Configure el
playbook para usar el módulo ansible.posix.at para programar una tarea que se
ejecute un minuto en el futuro.
La tarea debe ejecutar el comando date y redirigir la salida al archivo /home/devops/
my_at_date_time.
Use la opción unique: true para asegurarse de que, si el comando ya existe en la cola
at, no se agregue una nueva tarea.
4.1.
Cree el playbook schedule_at_task.yml y agregue las siguientes líneas:
---
- name: Schedule at task
  hosts: webservers
  become: true
  become_user: devops
  tasks:
    - name: Create date and time file
      ansible.posix.at:
        command: date > ~/my_at_date_time
        count: 1
        units: minutes
        unique: true
        state: present

Cree el playbook set_default_boot_target_graphical.yml en el directorio

5.1.
Cree el playbook set_default_boot_target_graphical.yml y agregue las
siguientes líneas:
---
- name: Change default boot target
  hosts: webservers
  become: true
  gather_facts: false
  vars:
    default_target: "graphical.target"
  tasks:
    - name: Get current boot target
      ansible.builtin.command:
        cmd: systemctl get-default
      changed_when: false
      register: target
    - name: Set default boot target
      ansible.builtin.command:
        cmd: systemctl set-default {{ default_target }}
      when: default_target not in target['stdout']

Administración del almacenamiento
Objetivos
• Particionar los dispositivos de almacenamiento, configurar LVM, formatear particiones o
volúmenes lógicos, montar sistemas de archivos y agregar espacios de intercambio (swap).
Montaje de sistemas de archivos existentes
Use el módulo ansible.posix.mount para montar un sistema de archivos existente. Los
parámetros más comunes para el módulo ansible.posix.mount son el parámetro path,
que especifica la ruta para montar el sistema de archivos, el parámetro src, que especifica
el dispositivo (esto podría ser un nombre de dispositivo, UUID o volumen NFS), el parámetro
fstype, que especifica el tipo de sistema de archivos, y el parámetro state, que acepta los
valores absent, mounted, present, unmounted o remounted.
La siguiente tarea de ejemplo monta el recurso compartido de NFS disponible en
172.25.250.100:/share en el directorio /nfsshare de los hosts gestionados.
- name: Mount NFS share
  ansible.posix.mount:
    path: /nfsshare
    src: 172.25.250.100:/share
    fstype: nfs
    opts: defaults
    dump: '0'
    passno: '0'
    state: mounted
Configuración de almacenamiento con el rol de
sistema de almacenamiento
Red Hat Ansible Automation Platform proporciona el rol del sistema
redhat.rhel_system_roles.storage para configurar dispositivos de almacenamiento
local en sus hosts gestionados. Puede gestionar sistemas de archivos en dispositivos de bloques
sin particiones y formatear y crear volúmenes lógicos en volúmenes físicos LVM basados en
dispositivos de bloques sin particiones.
Importante
El rol redhat.rhel_system_roles.storage soporta formalmente la gestión de
sistemas de archivos y las entradas de montaje para dos casos de uso:
• Dispositivos sin particiones (sistemas de archivos de dispositivos completos)
• LVM en volúmenes físicos de dispositivos completos sin particiones
Si tiene otros casos de uso, es posible que deba usar otros módulos y roles para
implementarlos.

Ejercicio Guiado
Administración de usuarios y
autenticación
Administrar usuarios y grupos, ajustar la configuración Sudo y configurar SSH en sus hosts
gestionados.
Resultados
• Crear un nuevo grupo de usuarios.
• Administrar usuarios mediante el módulo ansible.builtin.user.
• Completar claves SSH autorizadas con el módulo ansible.posix.authorized_key.
• Modificar el archivo /etc/ssh/sshd_config y un archivo de configuración en /etc/
sudoers.d usando el módulo ansible.builtin.lineinfile.
Antes De Comenzar
Con el usuario student en la máquina workstation, use el comando lab para preparar su
sistema para este ejercicio.
Este comando prepara su entorno y garantiza que estén disponibles todos los recursos
requeridos.
[student@workstation ~]$ lab start system-users
Instrucciones
Su organización requiere que todos los hosts tengan los mismos usuarios locales disponibles.
Estos usuarios deben pertenecer al grupo de usuarios webadmin, que tiene la capacidad de usar
el comando sudo sin especificar una contraseña. Además, las claves públicas SSH de los usuarios
deben distribuirse en el entorno para sus archivos ~/.ssh/authorized_keys para permitir la
autenticación basada en claves y no debe permitirse al usuario root iniciar sesión usando SSH
directamente.
Escriba un playbook para asegurarse de que los usuarios especificados en el archivo /home/
student/system-users/vars/users_vars.yml y el grupo de usuarios webadmin estén
presentes en los hosts gestionados y cumplan con los criterios anteriores.
 1.
Cambie al directorio /home/student/system-users.
[student@workstation ~]$ cd ~/system-users
[student@workstation system-users]$
 2.
Examine el archivo de variable vars/users_vars.yml existente.

Agregue una cláusula loop: "{{ users }}" a la tarea para iterar sobre cada
usuario encontrado en el archivo vars/users_vars.yml.
Para el parámetro name para los usuarios, use item['username'], no item. Esto
permite que cada ítem de la lista en el archivo de variables se estructure como un
diccionario de múltiples variables que incluye información adicional sobre cada
usuario en la lista, específicamente de qué grupos complementarios el usuario debe
ser miembro.
El playbook completo debería incluir el siguiente contenido:
---
- name: Create multiple local users
  hosts: webservers
  vars_files:
    - vars/users_vars.yml
  tasks:
    - name: Add webadmin group
      ansible.builtin.group:
        name: webadmin
        state: present
    - name: Create user accounts
      ansible.builtin.user:
        name: "{{ item['username'] }}"
        groups: "{{ item['groups'] }}"
      loop: "{{ users }}"

 5.
Asegúrese de que las claves públicas SSH se hayan distribuido correctamente
en el host remoto agregando una tercera tarea al play que use el módulo
ansible.posix.authorized_key.
En el directorio files, cada usuario tiene un único archivo de clave pública SSH. El
módulo recorre en bucle la lista de usuarios, encuentra la clave apropiada usando la variable
username y envía la clave al host gestionado.
Para el parámetro key, use la siguiente expresión Jinja2 para su valor para evaluar el
contenido del archivo de clave pública apropiado. Se usa una función de búsqueda con
el complemento (plug-in) file para leer el archivo y su nombre de archivo se construye
usando operaciones de cadena.
"{{ lookup('file', 'files/'+ item['username'] + '.key.pub') }}"
La tercera tarea debe contar con el siguiente contenido:
    - name: Add authorized keys
      ansible.posix.authorized_key:
        user: "{{ item['username'] }}"
        key: "{{ lookup('file', 'files/'+ item['username'] + '.key.pub') }}"
      loop: "{{ users }}"
 6.
Agregue una cuarta tarea al play que use el módulo ansible.builtin.lineinfile
para modificar el archivo de configuración sudo y permitir a los miembros del grupo
webadmin usar sudo sin una contraseña en el host gestionado. Use el parámetro
validate para validar la nueva entrada de configuración.
La cuarta tarea debe contar con el siguiente contenido:
    - name: Modify sudo config to allow webadmin users sudo without a password
      ansible.builtin.lineinfile:
        path: /etc/sudoers.d/webadmin
        state: present
        create: true
        mode: 0440
        line: "%webadmin ALL=(ALL) NOPASSWD: ALL"
        validate: /usr/sbin/visudo -cf %s

Administración del proceso de arranque y
procesos programados
Objetivos
• Administrar el inicio del servicio, programar procesos con at, cron y systemd, reiniciar los
hosts gestionados con reboot y controlar el destino de inicio predeterminado en los hosts
gestionados.
Programación de trabajos para la futura ejecución
Red Hat Enterprise Linux proporciona varios mecanismos que puede usar para programar
comandos a fin de que se ejecuten en algún momento en el futuro. El comando at programa
trabajos que se ejecutan una vez en un momento específico. El subsistema Cron programa
trabajos para que se ejecuten en un programa recurrente, ya sea en el archivo personal crontab
de un usuario, en la configuración Cron del sistema en /etc/crontab o como un archivo en
/etc/cron.d. El subsistema systemd también proporciona unidades de temporizador que
pueden iniciar unidades de servicio en un horario establecido.
Programación de trabajos que se ejecutan una sola vez
La programación rápida y de una vez se realiza con el módulo ansible.posix.at. Se crea la
tarea para que se ejecute en una hora futura y se la retiene hasta el momento de ejecutarse.
Opciones para el módulo ansible.posix.at
Opción
Comentarios
command
El comando para programar la ejecución en el futuro.
count
El número entero de unidades a partir de ahora que se debe
ejecutar el trabajo. (Debe usarse con units).
units
Especifica si count se mide en minutos, horas, días o
semanas.
script_file
Un archivo de script existente programado para que se ejecute
en el futuro.
state
El valor predeterminado (present) agrega un trabajo;
absent elimina un trabajo coincidente si está presente.
unique
Si se establece en true, si un trabajo coincidente ya está
presente, no se agrega un nuevo trabajo.

tempuser para que se ejecute en 20 minutos.

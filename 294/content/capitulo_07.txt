Descripción de la estructura del rol
Objetivos
• Describir el propósito de un rol de Ansible, su estructura y cómo se usan los roles en los
playbooks.
Estructuración de playbooks de Ansible con roles
A medida que desarrolla más playbooks, probablemente descubrirá que tiene muchas
oportunidades para volver a usar el código de playbooks que ya ha escrito. Tal vez podría volver
a usar un play para configurar una base de datos MySQL para una aplicación para configurar
una base de datos MySQL para otra aplicación, con diferentes nombres de host, contraseñas y
usuarios.
Ese play puede ser largo y complejo, con muchos archivos incluidos o importados, y con tareas y
manejadores para gestionar diversas situaciones. Copiar todo ese código en otro playbook podría
ser un trabajo no menor.
Los roles de Ansible facilitan la reutilización del código genérico de Ansible. Puede empaquetar
todas las tareas, variables, archivos, plantillas y otros recursos necesarios para aprovisionar
infraestructura o implementar aplicaciones en una estructura de directorios estandarizada. Copie
un rol de un proyecto a otro copiando el directorio, luego llame al rol dentro de un play.
Un rol bien escrito puede tomar variables pasadas del playbook. Estas variables pueden ajustar el
comportamiento de los roles mediante la configuración de todos los nombres de host específicos
del sitio, direcciones IP, nombres de usuario, contraseñas y otros detalles locales específicos.
Por ejemplo, podría escribir un rol con el fin de implementar un servidor de base de datos para
soportar variables que configuran el nombre de host, el usuario administrador de la base de datos
y la contraseña, y otros parámetros que necesitan personalización para su instalación.
También puede garantizar que se establezcan valores predeterminados razonables para esas
variables en el rol, si no se establecen en el play que invoca el rol.
Los roles Ansible tienen los siguientes beneficios:
• Los roles agrupan el contenido, lo que permite intercambiar el código fácilmente con otros.
• Los roles pueden definir los elementos fundamentales de un tipo de sistema, como un servidor
web, servidor de base de datos o repositorio de git.
• Los roles hacen que los proyectos más grandes sean más manejables.
• Los roles se pueden desarrollar en paralelo por diferentes usuarios.
Además de escribir, usar, volver a usar y compartir sus propios roles, puede obtener roles de
otras fuentes. Puede encontrar roles mediante el uso de paquetes de distribución, como Ansible
Content Collections. O puede descargar roles desde el centro de automatización de Red Hat, un
centro de automatización privado y desde el sitio web de Ansible Galaxy de la comunidad.
Red Hat Enterprise Linux incluye algunos roles en el paquete rhel-system-roles. Aprenderá
más sobre rhel-system-roles más adelante en este capítulo.

Análisis de la estructura de roles de Ansible
Una función Ansible se define mediante una estructura estandarizada de subdirectorios y archivos.
El directorio de nivel superior define el nombre del propio rol. Los archivos se organizan en
subdirectorios que se nombran de acuerdo con el propósito de cada archivo en el rol, como tasks
y handlers.
Los subdirectorios files y templates contienen archivos a los que hacen referencia tareas en
otros playbooks y archivos de tareas.
El siguiente comando tree muestra la estructura de directorio del rol user.example.
[user@host roles]$ tree user.example
user.example/
├── defaults
│   └── main.yml
├── files
├── handlers
│   └── main.yml
├── meta
│   └── main.yml
├── README.md
├── tasks
│   └── main.yml
├── templates
├── tests
│   ├── inventory
│   └── test.yml
└── vars
    └── main.yml

El archivo main.yml en este directorio contiene las definiciones de las
tareas de los roles.

Definición de variables y valores predeterminados
Las variables del rol se definen mediante la creación de un archivo vars/main.yml con pares de
clave-valor en la jerarquía del directorio del rol. Se hace referencia a estas variables en los archivos
de tareas de rol como cualquier otra variable: {{ VAR_NAME }}. Estas variables tienen una alta
prioridad y no se las puede reemplazar por variables de inventario. Estas variables son usadas por
el funcionamiento interno del rol.
Las variables predeterminadas permiten que se establezcan valores predeterminados para las
variables que se pueden usar en un play para configurar el rol o personalizar su comportamiento.
Estas variables se definen mediante la creación de un archivo defaults/main.yml con pares de
clave-valor en la jerarquía del directorio del rol. Las variables predeterminadas tienen la prioridad
más baja de cualquiera de las variables disponibles.
Los valores de las variables predeterminadas pueden reemplazarse con cualquier otra variable,
incluidas las variables de inventario. El objetivo de estas variables es proporcionarle a la persona
que escribe un play que utiliza el rol una manera de personalizar o controlar exactamente lo que
va a hacer. Puede usar las variables predeterminadas para proporcionarle información al rol de que
necesita configurar o implementar algo correctamente.
Defina una variable específica en vars/main.yml o defaults/main.yml, pero no en ambos
lugares. Utilice variables predeterminadas cuando desee que los valores de las variables se
reemplacen.
Importante
Los roles no deben tener datos específicos del sitio ni contener secretos como
contraseñas o claves privadas, ya que se supone que los roles son genéricos,
reutilizables y que se pueden compartir libremente. Por lo tanto, los detalles
específicos del sitio no deben ser codificados en ellos.
Los secretos deben proporcionarse al rol a través de otros medios. Este requisito es
una de las razones por las que puede querer establecer variables de rol al invocar a
un rol. Las variables de rol establecidas en el play podrían proporcionar el secreto, o
apuntar a un archivo cifrado por Ansible Vault que contenga el secreto.

Importación e inclusión de roles como tareas
Los roles se pueden agregar a un play mediante una tarea ordinaria. Use el módulo
ansible.builtin.import_role para importar estadísticamente un rol y el módulo
ansible.builtin.include_role para incluir dinámicamente un rol.
El siguiente play muestra cómo se puede importar un rol usando una tarea con el módulo
ansible.builtin.import_role. El play de ejemplo ejecuta la tarea A normal task
primero, luego importa el rol role2.
- name: Run a role as a task
  hosts: remote.example.com
  tasks:
    - name: A normal task
      ansible.builtin.debug:
        msg: 'first task'
    - name: A task to import role2 here
      ansible.builtin.import_role:
        name: role2
Con el módulo ansible.builtin.import_role, Ansible trata el rol como una importación
estática y lo analiza durante el procesamiento inicial del playbook.
En el ejemplo anterior, cuando se analiza el playbook:
• Si roles/role2/tasks/main.yml existe, Ansible agrega las tareas en ese archivo al play.
• Si roles/role2/handlers/main.yml existe, Ansible agrega los manejadores en ese archivo
al play.
• Si roles/role2/defaults/main.yml existe, Ansible agrega las variables predeterminadas
en ese archivo al play.
• Si roles/role2/vars/main.yml existe, Ansible agrega las variables en ese archivo al
play (posiblemente anulando los valores de las variables predeterminadas del rol debido a la
precedencia).
Importante
Debido a que ansible.builtin.import_role se procesa cuando se analiza
el playbook, los manejadores del rol, las variables predeterminadas y las variables
del rol están expuestas a todas las tareas y funciones del play y se puede acceder a
ellas mediante tareas y funciones que la preceden en el play (incluso aunque el rol
todavía no se haya ejecutado).

Una diferencia clave entre los dos módulos es cómo manejan las palabras clave, los condicionales y
los bucles al nivel de tarea:
• ansible.builtin.import_role aplica los condicionales y los bucles de la tarea a cada una
de las tareas que se importan.
• ansible.builtin.include_role aplica los condicionales y los bucles de la tarea a la
declaración que determina si el rol está incluido o no.
Además, cuando incluye un rol, sus variables de rol y las variables predeterminadas no se exponen
al resto del play, a diferencia de ansible.builtin.import_role.
Uso de una sección de roles en un play
Otra forma de invocar roles en un play es enumerarlos en una sección roles. La sección roles
es muy similar a la sección tasks, excepto que en lugar de consistir en una lista de tareas,
consiste en una lista de roles.
En el siguiente play de ejemplo, se ejecuta el rol role1 y, a continuación, se ejecuta el rol role2.
---
- name: A play that only has roles
  hosts: remote.example.com
  roles:
    - role: role1
    - role: role2
Por cada rol especificado, las tareas, los manejadores, las variables y las dependencias de los roles
se importan al play en el orden en que aparecen en la lista.
Cuando usa una sección roles para importar roles a un play, los roles se ejecutan primero, antes
que cualquier tarea que defina para ese play. No importa si la sección roles aparece antes o
después de la sección tasks en el play.
---
- name: Roles run before tasks
  hosts: remote.example.com
  tasks:
    - name: A task
      ansible.builtin.debug:

Debido a que los roles se ejecutan primero, generalmente tiene sentido enumerar la sección

  hosts: remote.example.com

  tasks:
    - name: A task.
      ansible.builtin.debug:
        msg: "This task runs after the role."
Importante
No se requiere una sección tasks en un play. De hecho, generalmente es
una buena práctica evitar las secciones roles y tasks en un play para evitar
confusiones sobre el orden en que se ejecutan los roles y las tareas.
Si debe tener una sección tasks y roles, es mejor crear tareas que usen
ansible.builtin.import_role y ansible.builtin.include_role para
que se ejecuten en los puntos correctos en la ejecución del play.
En el siguiente ejemplo, se establecen valores para dos variables de rol de role2, var1 y var2.
Las variables defaults y vars se anulan cuando se usa role2.

- name: A play that runs the second role with variables

- name: A play that runs the second role with variables

Importante
Ansible busca líneas de roles duplicadas en la sección roles. Si se enumeran dos
roles con exactamente los mismos parámetros, el rol solo se ejecuta una vez.
Por ejemplo, la siguiente sección roles solo ejecuta role1 una vez:
roles:
  - { role: role1, service: "httpd" }
  - { role: role2, var1: true }
  - { role: role1, service: "httpd" }
Para ejecutar el mismo rol por segunda vez, debe tener diferentes parámetros
definidos:
roles:
  - { role: role1, service: "httpd" }
  - { role: role2, var1: true }
  - { role: role1, service: "postfix" }
Secciones de tareas especiales
Hay dos secciones de tareas especiales, pre_tasks y post_tasks, que se usan ocasionalmente
con las secciones roles. La sección pre_tasks es una lista de tareas, similar a tasks, pero
estas tareas se ejecutan antes que cualquiera de los roles en la sección roles. Si alguna de las
tareas en la sección pre-tasks notifica a un manejador, las tareas del manejador se ejecutan
antes que los roles o las tareas normales.
Los plays también soportan una palabra clave post_tasks. Estas tareas se ejecutan después de
las tasks del play y los manejadores notificados por las tasks del play.
El siguiente play muestra un ejemplo con pre_tasks, roles, tasks, post_tasks y handlers.
Es raro que un play tenga todas estas secciones.
- name: Play to illustrate order of execution
  hosts: remote.example.com
  pre_tasks:
    - name: This task runs first
      ansible.builtin.debug:
        msg: This task is in pre_tasks
      notify: my handler
      changed_when: true
  roles:
    - role: role1
  tasks:
    - name: This task runs after the roles
      ansible.builtin.debug:
        msg: This task is in tasks
      notify: my handler
      changed_when: true
  post_tasks:
    - name: This task runs last
      ansible.builtin.debug:

Creación de roles
Objetivos
• Cree un rol en el directorio de proyectos de un playbook y ejecútelo como parte de uno de los
plays del playbook.
El proceso de creación de roles
Crear roles en Ansible no requiere herramientas de desarrollo especiales.
Crear y usar un rol es un proceso de tres pasos:
1.
Cree la estructura del directorio de roles.
2.
Defina el contenido de los roles.
3.
Use el rol en un playbook.
Creación de la estructura del directorio de roles
Ansible busca roles en un subdirectorio llamado roles en el directorio que contiene el playbook
de Ansible. Cada rol tiene su propio directorio con una estructura de directorios estandarizada.
Esta estructura le permite almacenar roles con el playbook y otros archivos de soporte.
Por ejemplo, la siguiente estructura de directorio contiene los archivos que definen el rol motd.
[user@host ~]$ tree roles/
roles/
└── motd
    ├── defaults
    │   └── main.yml
    ├── files
    ├── handlers
    ├── meta
    │   └── main.yml
    ├── README.md
    ├── tasks
    │   └── main.yml
    └── templates
        └── motd.j2
README.md proporciona, en términos legibles para el ser humano, una descripción básica del
rol, documentación y ejemplos de cómo usarlo, y todos los requisitos de roles ajenos a Ansible. El
subdirectorio meta contiene un archivo main.yml que especifica información sobre el autor, la
licencia, la compatibilidad y las dependencias del módulo.
El subdirectorio files contiene archivos de contenido fijo y el subdirectorio templates contiene
plantillas que puede implementar el rol.

Creación de un esqueleto de roles
Puede crear todos los subdirectorios y archivos necesarios para un rol nuevo mediante comandos
estándares de Linux. Como alternativa, existen utilidades de línea de comandos para automatizar
el proceso de creación de nuevos roles.
La herramienta de línea de comandos ansible-galaxy (que se analiza en más detalle más
adelante en este curso) se usa para administrar los roles de Ansible, incluida la creación de nuevos
roles. Puede ejecutar ansible-galaxy role init para crear la estructura de directorios
para un nuevo rol. Especifique el nombre del rol como argumento del comando, lo que crea un
subdirectorio para el nuevo rol en el directorio de trabajo actual.
[user@host playbook-project]$ cd roles
[user@host roles]$ ansible-galaxy role init my_new_role
- Role my_new_role was created successfully
[user@host roles]$ ls my_new_role/
defaults  files  handlers  meta  README.md  tasks  templates  tests  vars
Definición del contenido de los roles

ejecutadas por el rol.

Prácticas recomendadas para el desarrollo de contenido de rol
Los roles le permiten dividir los playbooks en varios archivos, lo que da como resultado un código
reutilizable. Para maximizar la eficacia de los roles recién desarrollados, considere implementar las
siguientes prácticas recomendadas en el desarrollo de roles:
• Mantenga cada rol en su propio repositorio de control de versiones. Ansible funciona bien con
repositorios basados en Git.
• Use variables para configurar roles de modo que pueda volver a usar el rol para realizar tareas
similares en circunstancias similares.
• Evite almacenar información confidencial en un rol, como contraseñas o claves SSH. Configure
las variables de rol que se usan para contener valores confidenciales cuando se llaman en un
play con valores predeterminados que no son confidenciales. Los playbooks que usan el rol son
responsables de definir variables sensibles a través de archivos de variables de Ansible Vault u
otros métodos.
• Use el comando ansible-galaxy role init para iniciar su rol y, luego, elimine los archivos
y directorios innecesarios.
• Cree y mantenga archivos README.md y meta/main.yml para documentar el propósito, el
autor y el uso del rol.
• Mantenga su rol enfocado en un propósito o una función específicos. En lugar de escribir un rol
que haga muchas cosas, escriba más de un rol.
• Vuelva a usar los roles con frecuencia.
Evite crear nuevos roles para las configuraciones perimetrales. Si un rol existente sirve para la
mayoría de la configuración requerida, refactorice el rol existente para integrar el nuevo escenario
de configuración.
Use técnicas de prueba de integración y regresión para asegurarse de que el rol proporcione la
nueva funcionalidad requerida y que no cause problemas a los playbooks existentes.

Cambio del comportamiento de un rol con variables
Un rol bien redactado usa variables predeterminadas para alterar el comportamiento del rol para
que coincida con un escenario de configuración relacionado. Los roles que usan variables son más
genéricos y reutilizables en una variedad de contextos.
El valor de cualquier variable definida en el directorio defaults de un rol se sobrescribirá si se
define esa misma variable:
• En un archivo de inventario, como una variable de host o una variable de grupo.
• En un archivo YAML en los directorios group_vars o host_vars de un proyecto de playbook.
• Como una variable anidada en la palabra clave vars de un play.
• Como una variable cuando se incluye el rol en la palabra clave roles de un play.
En el siguiente ejemplo, se muestra cómo usar el rol motd con un valor diferente para la variable
del rol system_owner. El valor especificado, someone@host.example.com, reemplazará a la
referencia de variable cuando se aplique el rol a un host gestionado.
[user@host ~]$ cat use-motd-role.yml
---
- name: use motd role playbook
  hosts: remote.example.com
  remote_user: devops
  become: true
  vars:
    system_owner: someone@host.example.com
  roles:
    - role: motd
Cuando se define de esta manera, la variable system_owner reemplaza el valor de la variable
predeterminada del mismo nombre. Todas las definiciones de variables anidadas dentro de la
palabra clave vars no reemplazarán el valor de la misma variable si se la define en el directorio
vars de un rol.

Importante
La precedencia de variables puede causar confusión al trabajar con variables de rol
en un play.
• La mayoría de las otras variables anulan las variables predeterminadas de un rol:
variables de inventario, vars de play, parámetros de rol en línea, etc.
• Menos variables pueden anular las variables definidas en el directorio vars
de un rol. Los datos, las variables cargadas con include_vars, las variables
registradas y los parámetros de rol pueden anular estas variables. Las variables de
inventario y vars de play no pueden hacerlo. Este comportamiento es importante
porque ayuda a evitar que el play modifique accidentalmente el funcionamiento
interno del rol.
• Las variables declaradas en línea como parámetros de rol tienen una prioridad
muy alta; también pueden anular las variables definidas en el directorio vars de
un rol.
Si un parámetro de rol tiene el mismo nombre que una variable establecida en vars
del play, un vars de rol o una variable de inventario o playbook, el parámetro de rol
anulará a la otra variable.
Definición de las dependencias del rol
Las dependencias del rol permiten que un rol incluya otros roles como dependencias.
Por ejemplo, un rol que define un servidor de documentación puede depender de otro rol que
instale y configure un servidor web.
Las dependencias se definen en el archivo meta/main.yml en la jerarquía del directorio del rol.
El siguiente es un archivo meta/main.yml de muestra.
---
dependencies:
  - role: apache
    port: 8080
  - role: postgres
    dbname: serverlist
    admin_user: felix
nota
Un archivo meta/main.yml también puede tener una clave galaxy_info de
nivel superior que tiene un diccionario de otros atributos que especifican el autor, el
propósito, la licencia y las versiones de Ansible Core y los sistemas operativos que el
rol soporta.

Implementación de roles desde fuentes
externas de contenido
Objetivos
• Seleccionar y recuperar roles de fuentes externas, como repositorios de Git o Ansible Galaxy, y
usarlos en sus playbooks.
Fuentes de contenido externo
Si está usando roles en sus playbooks de Ansible, debe obtener esos roles de alguna fuente
administrada centralmente. Esta práctica garantiza que todos sus proyectos tengan la versión
actual del rol y que cada proyecto pueda beneficiarse de las correcciones de errores descubiertas
por otros proyectos con los que comparten el rol.
Por ejemplo, si el rol es contenido privado creado y coordinado por su organización, podría
almacenarse en un repositorio de Git administrado por su organización. Alternativamente, podría
distribuirse como un archivo de almacenamiento tar desde un sitio web o por otros medios.
Además, la comunidad de código abierto mantiene algunos roles a través del sitio web de Ansible
Galaxy. Red Hat no son revisa ni respalda oficialmente estos roles, pero pueden contener código
que su organización considere útil.

Obtención de roles y módulos de las
colecciones de contenido
Objetivos
• Obtener un conjunto de roles relacionados, módulos suplementarios y otro contenido de Ansible
Content Collection y usarlos en un playbook.
Ansible Content Collections
Cuando se desarrolló Ansible por primera vez, todos los módulos que usaba se incluían como
parte del paquete de software central (core). A medida que aumentaba la cantidad de módulos, se
hizo más difícil para el proyecto upstream gestionar todos estos módulos. Cada módulo requería
un nombre único y sincronizar las actualizaciones del módulo con las actualizaciones del código
central (core) de Ansible.
Con Ansible Content Collections, las actualizaciones del código Ansible se separan de las
actualizaciones de módulos y complementos (plug-ins). Una Ansible Content Collection
proporciona un conjunto de módulos, roles y otros complementos (plug-ins) relacionados que
puede usar en sus playbooks. Este enfoque permite a los proveedores y desarrolladores mantener
y distribuir sus colecciones a su propio ritmo, independientemente de las versiones de Ansible.
Por ejemplo:
• La colección de contenido redhat.insights ofrece módulos y roles que puede usar para
registrar un sistema con Red Hat Insights para Red Hat Enterprise Linux.
• La colección de contenido cisco.ios, soportada y mantenida por Cisco, ofrece módulos y
complementos (plug-ins) que administran dispositivos de red de Cisco IOS.
• La colección de contenido community.crypto proporciona módulos que crean certificados
SSL/TLS.
Ansible Content Collections también brindan flexibilidad. Puede instalar solo el contenido que
necesita en lugar de instalar todos los módulos soportados.
También puede seleccionar una versión específica de una colección (posiblemente una anterior
o posterior) o elegir entre una versión de una colección compatible con Red Hat o proveedores, o
una proporcionada por la comunidad.
Ansible 2.9 y posteriores admiten Ansible Content Collections. Upstream Ansible separó la
mayoría de los módulos del código central de Ansible en Ansible Base 2.10 y Ansible Core 2.11 y
los colocó en colecciones. Red Hat Ansible Automation Platform 2.2 proporciona entornos de
ejecución de automatización basados en Ansible Core 2.13 que heredan esta característica.
nota
Puede desarrollar sus propias colecciones para proporcionar roles y módulos
personalizados a sus equipos. La creación de Ansible Content Collections por su
cuenta está fuera del alcance de este curso. Puede obtener más información sobre
cómo crear Ansible Content Collections en el curso que sigue a este, Desarrollo de
automatización avanzada con Red Hat Ansible Automation Platform (DO374).

Espacios de nombres para Ansible Content Collections
Para facilitar la especificación de las colecciones y su contenido por nombre, los nombres de las
colecciones se organizan en espacios de nombres. Los proveedores, socios, desarrolladores y
creadores de contenido pueden usar espacios de nombres para asignar nombres únicos a sus
colecciones sin entrar en conflicto con otras colecciones.
El espacio de nombres es la primera parte de un nombre de colección. Por ejemplo, todas
las colecciones que la comunidad Ansible mantiene están en el espacio de nombres
community y tiene nombres tales como community.crypto, community.postgresql y
community.rabbitmq. Asimismo, Ansible Content Collections que Red Hat mantiene y admite
directamente pueden usar el espacio de nombres redhat y tener nombres como redhat.rhv,
redhat.satellite y redhat.insights.
Selección de fuentes de Ansible Content Collections
Independientemente de si está usando ansible-navigator con el entorno de ejecución de
automatización mínima o ansible-playbook en Ansible Core bare metal, siempre tiene al
menos una Ansible Content Collection disponible: ansible.builtin.
Además, su entorno de ejecución de automatización puede tener entornos de ejecución de
automatización adicionales integrados, por ejemplo, el entorno de ejecución predeterminado
usado por Red Hat Ansible Automation Platform 2.2, ee-supported-rhel8.
Si necesita tener Ansible Content Collections adicionales, puede agregarlas al subdirectorio
collections de su proyecto Ansible. Puede obtener Ansible Content Collections de varias
fuentes:
Automation Hub
El centro de automatización es un servicio proporcionado por Red Hat para distribuir Ansible
Content Collections certificadas por Red Hat que son compatibles con Red Hat y los partners
del ecosistema. Como cliente final, puede abrir un ticket de soporte con Red Hat para estas
Ansible Content Collections que serán abordadas por Red Hat y el partner del ecosistema.
Necesita una suscripción válida a Red Hat Ansible Automation Platform para acceder al centro
de automatización. Use la interfaz de usuario web del centro de automatización en https://
console.redhat.com/ansible/automation-hub/ para explorar estas colecciones.
Centro de automatización privado
Su organización puede tener su propio centro de automatización privado en el sitio y también
puede usar ese centro para distribuir sus propias Ansible Content Collections. El centro de
automatización privado se incluye en Red Hat Ansible Automation Platform.
Ansible Galaxy
Ansible Galaxy es un sitio web respaldado por la comunidad que alberga Ansible Content
Collections que han sido enviadas por una variedad de desarrolladores y usuarios de
Ansible. Ansible Galaxy es una librería pública que no ofrece garantías formales de soporte
y que no está organizada por Red Hat. Por ejemplo, las colecciones community.crypto,
community.postgresql y community.rabbitmq están disponibles en esa plataforma.
Use la interfaz de usuario web de Ansible Galaxy en https://galaxy.ansible.com/ para buscar
colecciones.
Repositorio de Git de terceros o archivo de almacenamiento
También puede descargar Ansible Content Collections desde un repositorio de Git o un
archivo de almacenamiento local o remoto tar, al igual que puede descargar roles.

Instalación de Ansible Content Collections
Antes de que sus playbooks puedan usar contenido de una Ansible Content Collection, debe
asegurarse de que la colección esté disponible en su entorno de ejecución de automatización.
El ajuste de configuración de Ansible collections_paths especifica una lista separada por dos
puntos de rutas en el sistema donde Ansible busca colecciones instaladas.
Puede establecer esta directiva en el archivo de configuración ansible.cfg.
Importante
El siguiente valor predeterminado hace referencia a la directiva
collections_paths.
~/.ansible/collections:/usr/share/ansible/collections
Si establece collections_paths en algún otro valor en el archivo ansible.cfg
de su proyecto Ansible y elimina esos dos directorios, entonces ansible-
navigator no puede encontrar las Ansible Content Collections proporcionadas
dentro del entorno de ejecución de automatización en su versión de esos
directorios.
El siguiente ejemplo usa el comando ansible-galaxy collection install para descargar
e instalar la Ansible Content Collection community.crypto. La opción -p collections
instala la colección en el subdirectorio local collections.
[user@controlnode ~]$ ansible-galaxy collection install community.crypto \
> -p collections
Importante
Debe especificar la opción -p collections o ansible-galaxy instala la
colección en función de su configuración actual collections_paths, o en
su directorio ~/.ansible/collections/ en el nodo de control de forma
predeterminada. El comando ansible-navigator no carga este directorio en el
entorno de ejecución de la automatización, aunque este directorio está disponible
para los comandos de Ansible que usan el nodo de control como entorno de
ejecución, como ansible-playbook.
Cuando instala la colección community.crypto, es posible que vea una advertencia de que los
playbooks de su proyecto de Ansible podrían no encontrar la colección porque la ruta especificada
no forma parte de la ruta configurada de las colecciones de Ansible.
Puede ignorar esta advertencia con seguridad porque su proyecto Ansible verifica el subdirectorio
local collections antes de verificar los directorios especificados por la configuración
collections_paths y puede usar las colecciones almacenadas allí.
El comando también puede instalar una colección desde un archivo tar local o remoto o un
repositorio de git. Un repositorio de Git debe tener un archivo galaxy.yml o MANIFEST.json
válido que proporcione metadatos sobre la colección, como su espacio de nombres y número de
versión. Por ejemplo, consulte la colección community.general en https://github.com/
ansible-collections/community.general.

Instalación de Ansible Content Collections con un archivo de
requisitos
Si su proyecto de Ansible necesita colecciones de contenido de Ansible adicionales, puede crear
un archivo collections/requirements.yml en el directorio del proyecto que enumera todas
las colecciones que requiere el proyecto. El controlador de automatización detecta este archivo e
instala automáticamente las colecciones especificadas antes de ejecutar sus playbooks.
Un archivo de requisitos para Ansible Content Collections es un archivo YAML que consta de una
clave de diccionario collections que tiene la lista de colecciones para instalar como su valor.
Cada ítem de la lista también puede especificar la versión particular de la colección para instalar,
como se muestra en el siguiente ejemplo:
---
collections: 
  - name: community.crypto 
  - name: ansible.posix
    version: 1.2.0 
  - name: /tmp/community-dns-1.2.0.tar.gz 
  - name: http://www.example.com/redhat-insights-1.0.5.tar.gz 
  - name: git+https://github.com/ansible-collections/community.general.git 
    version: main
El valor de esta clave de diccionario es la lista de colecciones requeridas por el proyecto
Ansible.
Instale Ansible Content Collection community.crypto desde la primera fuente disponible.
La siguiente parte de esta sección abarca cómo configurar las fuentes.
Instale la versión 1.2.0 de la Ansible Content Collection ansible.posix desde la primera
fuente disponible. Es una buena práctica especificar la versión siempre que sea posible.
Instale una Ansible Content Collection desde un archivo de almacenamiento local tar en
particular.
Instale una Ansible Content Collection desde el archivo tar en la URL remota especificada.
Instale Ansible Content Collection community.general desde un repositorio público de
Git, seleccionando la versión en la rama main. La directiva version puede ser una rama, una
etiqueta o un hash de confirmación.

Objetivos
• Escribir playbooks que aprovechen los roles del sistema de Red Hat Enterprise Linux para

Roles de sistema
Roles del sistema son un conjunto de roles de Ansible que puede usar para configurar y gestionar
diversos componentes, subsistemas y paquetes de software incluidos en Red Hat Enterprise
Linux. Los roles del sistema proporcionan automatización para muchas tareas comunes de
configuración del sistema, incluida la sincronización de la hora, las redes, el firewall, el ajuste y el
registro.
Estos roles están destinados a proporcionar una API de automatización que sea uniforme en
varias versiones principales y secundarias de Red Hat Enterprise Linux. El artículo de la base
de conocimiento en https://access.redhat.com/articles/3050101 documenta las
versiones de Red Hat Enterprise Linux en sus hosts gestionados que admiten roles específicos.
Gestión simplificada de la configuración
Los roles del sistema pueden ayudarlo a simplificar la automatización en varias versiones de
Red Hat Enterprise Linux. Por ejemplo, el servicio de sincronización de hora recomendado es
diferente en diferentes versiones de Red Hat Enterprise Linux.
• Se prefiere el servicio chronyd en RHEL 9.
• Se prefiere el servicio ntpd en RHEL 6.
En un entorno con una combinación de versiones de Red Hat Enterprise Linux, debe gestionar los
archivos de configuración para ambos servicios.
Puede usar un playbook de Ansible que ejecute el rol redhat.rhel_system_roles.timesync
para configurar la sincronización de la hora para los hosts gestionados que ejecutan cualquiera de
las versiones de Red Hat Enterprise Linux.
Con los roles del sistema, ya no necesita mantener los archivos de configuración para ambos
servicios.
Soporte para roles de sistema
Los roles del sistema se proporcionan como Ansible Content Collections
redhat.rhel_system_roles certificadas por Red Hat a través del centro de automatización
para los clientes de Red Hat Ansible Automation Platform, como parte de su suscripción.
Además, los roles se proporcionan como un paquete RPM (rhel-system-roles) con Red Hat
Enterprise Linux 9 para su uso con la versión de Ansible Core proporcionada por ese sistema
operativo. Estos roles del sistema tienen los mismos beneficios de soporte de ciclo de vida que la
suscripción a Red Hat Enterprise Linux.
La mayoría de los roles de sistema son "totalmente soportados" y tienen interfaces estables.

Resumen
• Los roles de Ansible lo ayudan a volver a usar y compartir el código de Ansible.
• Ansible Content Collections_ distribuye roles, módulos y otros complementos (plug-ins) de
Ansible relacionados que puede usar en proyectos de Ansible y entornos de ejecución de
automatización.
• Use el comando ansible-galaxy para gestionar los roles de Ansible y Ansible Content
Collections.
• Red Hat proporciona Ansible Content Collections certificadas por Red Hat a través de un
centro de automatización de servicios basados en la nube. Red Hat y sus partners admiten estas
Ansible Content Collections.
• Puede distribuir Ansible Content Collections certificadas por Red Hat o sus propias Ansible
Content Collections desde un centro de automatización privado en las instalaciones.
• Ansible Galaxy proporciona una librería de roles de Ansible de terceros y Ansible Content
Collections que son gestionadas por la comunidad y no son admitidas por Red Hat.
• Los roles del sistema (redhat.rhel_system_roles) se proporcionan como un paquete
RPM o como una Ansible Content Collection que consta de varios roles destinados a ayudarlo a
configurar subsistemas de hosts gestionados en varias versiones de Red Hat Enterprise Linux.
• Los roles y Ansible Content Collections que necesita un proyecto se pueden especificar
mediante archivos requirements.yml y se pueden instalar en su proyecto de Ansible
manualmente mediante ansible-galaxy.

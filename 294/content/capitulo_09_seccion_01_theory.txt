Administración de paquetes con Ansible
El módulo ansible.builtin.dnf de Ansible usa dnf en los hosts gestionados para manejar las
operaciones de paquetes. El siguiente playbook instala el paquete httpd en el host gestionado
servera.lab.example.com:
---
- name: Install the required packages on the web server
  hosts: servera.lab.example.com
  tasks:
    - name: Install the httpd packages
      ansible.builtin.dnf:
        name: httpd    
        state: present 
La palabra clave name especifica el nombre del paquete para instalar.
La palabra clave state indica el estado esperado del paquete en el host gestionado:
present
Ansible instala el paquete si aún no está instalado.
absent
Ansible elimina el paquete si está instalado.
latest
Ansible actualiza el paquete si aún no está en la versión más reciente disponible. Si el
paquete no está instalado, Ansible lo instala.
La siguiente tabla compara algunos usos del módulo de Ansible ansible.builtin.dnf con el
comando equivalente dnf.
Tarea de Ansible
Comando DNF
- name: Install httpd
  ansible.builtin.dnf:
    name: httpd
    state: present
dnf install httpd

Optimización de la instalación de varios paquetes
Para operar en varios paquetes, la palabra clave name acepta una lista. El siguiente playbook
instala tres paquetes en el host gestionado servera.lab.example.com.
---
- name: Install the required packages on the web server
  hosts: servera.lab.example.com
  tasks:
    - name: Install the packages
      ansible.builtin.dnf:
        name:
          - httpd
          - mod_ssl
          - httpd-tools
        state: present
Con esta sintaxis, Ansible instala los paquetes en una sola transacción de DNF. Esto es equivalente
a ejecutar el comando dnf install httpd mod_ssl httpd-tools.
Una versión más común pero menos eficiente y más lenta de esta tarea es usar un bucle.
---
- name: Install the required packages on the web server
  hosts: servera.lab.example.com
  tasks:
    - name: Install the packages
      ansible.builtin.dnf:
        name: "{{ item }}""
        state: present
      loop:
        - httpd
        - mod_ssl
        - httpd-tools
Evite usar este método, ya que requiere que el módulo realice tres transacciones individuales, una
para cada paquete.
Recopilación de datos sobre paquetes instalados
El módulo de Ansible ansible.builtin.package_facts recopila los detalles del paquete
instalado en los hosts gestionados. Establece la variable ansible_facts['packages'] con los
detalles del paquete.

Revisión de módulos alternativos para administrar paquetes
Para otros administradores de paquetes, Ansible generalmente proporciona un módulo dedicado.
El módulo ansible.builtin.apt usa la herramienta de paquetes APT disponible en Debian o
Ubuntu. El módulo ansible.windows.win_package puede instalar software en sistemas de
Microsoft Windows.
El playbook siguiente usa condicionales para seleccionar el módulo apropiado en un entorno
compuesto por sistemas de Red Hat Enterprise Linux que ejecuta las versiones principales 7, 8 y 9.
---
- name: Install the required packages on the web servers
  hosts: webservers
  tasks:
    - name: Install httpd on RHEL 8 and 9
      ansible.builtin.dnf:
        name: httpd
        state: present
      when:
        - "ansible_facts['distribution'] == 'RedHat'"
        - "ansible_facts['distribution_major_version'] >= '8'`"
    - name: Install httpd on RHEL 7 and earlier
      `ansible.builtin.yum:
        name: httpd
        state: present
      when:
        - "ansible_facts['distribution'] == 'RedHat'"
        - "ansible_facts['distribution_major_version'] <= `'7'`"

Registro y gestión de sistemas con Red Hat
Subscription Management
Puede habilitar sus sistemas Red Hat Enterprise Linux para suscripciones de productos mediante
el uso de algunos métodos diferentes:
• Puede usar el comando subscription-manager.
• En los sistemas Red Hat Enterprise Linux 9.2 y posteriores, puede usar el rol rhel-system-
roles.rhc disponible en el RPM rhel-system-roles (versión 1.21.1 y posteriores).
• Puede usar el rol redhat.rhel_system_roles.rhc de la colección
redhat.rhel_system_roles (versión 1.21.1 y posteriores).

Gestión de Red Hat Subscription Management mediante el uso
de un rol
Ya sea que use el rol rhel-system-roles.rhc del RPM rhel-system-roles o el rol
redhat.rhel_system_roles.rhc de la colección redhat.rhel_system_roles, los pasos
para administrar la gestión de suscripciones a Red Hat son esencialmente los mismos.
1.
Cree un play que incluya el rol deseado:
---
- name: Register systems
  hosts: all
  become: true
  tasks:
    - name: Include the rhc role
      ansible.builtin.include_role:
        name: redhat.rhel_system_roles.rhc
2.
Defina las variables para el rol. Puede definir estas variables en el play, en un directorio
group_vars, en un directorio host_vars o en un archivo de variables separado:
---
rhc_state: present 
rhc_auth: 
  login:
    username: yourusername
    password: yourpassword
rhc_insights: 
  state: present

  - name: rhel-9-for-x86_64-baseos-rpms
    state: enabled
  - name: rhel-9-for-x86_64-appstream-rpms
    state: enabled

La variable rhc_state especifica si el sistema debe estar conectado (o registrado) a
Red Hat. Los valores válidos son present, absent y reconnect. Cuando se establece
en present o reconnect, el rol intenta conectar automáticamente una suscripción.
La variable rhc_auth define variables adicionales relacionadas con la autenticación
en la gestión de suscripciones a Red Hat, como las variables rhc_auth['login'] y
rhc_auth['activation_keys']. Una opción para la autenticación es especificar su
nombre de usuario y contraseña. Si usa esta opción, puede considerar proteger estas
variables con Ansible Vault. Una segunda opción es definir claves de activación para su
organización.
La variable rhc_insights define variables adicionales relacionadas con Red Hat
Insights. De manera predeterminada, la variable rhc_insights['state']
tiene un valor de present, que habilita la integración de Red Hat Insights.
Hay variables adicionales disponibles para Red Hat Insights cuando la variable
rhc_insights['state'] tiene un valor de present. Establezca la variable
rhc_insights['state'] en absent para deshabilitar la integración de Red Hat
Insights.
La variable rhc_repositories define una lista de repositorios para habilitar o
deshabilitar.
3.
Después de crear el playbook y definir las variables para el rol, ejecute el playbook para aplicar
la configuración.
Configuración de un repositorio de paquetes RPM
Para habilitar el soporte para un repositorio Yum de terceros en un host gestionado, Ansible
proporciona el módulo ansible.builtin.yum_repository.
Configuración de un repositorio de paquetes RPM
Cuando se ejecuta, el playbook siguiente declara un nuevo repositorio Yum en
servera.lab.example.com.
---
- name: Configure the company YUM/DNF repositories
  hosts: servera.lab.example.com
  tasks:
    - name: Ensure Example Repo exists
      ansible.builtin.yum_repository:
        file: example   
        name: example-internal
        description: Example Inc. Internal YUM/DNF repo
        baseurl: http://materials.example.com/yum/repository/
        enabled: true
        gpgcheck: true   
        state: present  
La palabra clave file especifica el nombre del archivo que se creará en el directorio /etc/
yum.repos.d/. El módulo agrega automáticamente la extensión .repo a ese nombre.

RPM no instala ningún paquete cuya firma GPG no coincide. Use el módulo de Ansible
ansible.builtin.rpm_key, descrito más adelante en esta sección, para instalar la clave
GPG pública requerida.
Al configurar la palabra clave state en present, Ansible crea o actualiza el archivo .repo.
Al configurar state en absent, Ansible elimina el archivo.
El archivo /etc/yum.repos.d/example.repo resultante en servera.lab.example.com es
de la siguiente forma:
[example-internal]
async = 1
baseurl = http://materials.example.com/yum/repository/
enabled = 1
gpgcheck = 1
name = Example Inc. Internal YUM/DNF repo
El módulo ansible.builtin.yum_repository expone la mayoría de los parámetros de
configuración del repositorio como palabras clave. Ejecute el comando ansible-navigator
doc ansible.builtin.yum_repository para obtener ejemplos de parámetros y de
playbooks adicionales.
nota
Algunos repositorios de terceros proporcionan el archivo de configuración y la
clave pública de GPG como parte del paquete de RPM que puede descargarse e
instalarse con el comando dnf install.

Para este repositorio, use el módulo ansible.builtin.dnf para instalar el
paquete EPEL en lugar del módulo ansible.builtin.yum_repository.
Importación de una clave GPG de RPM
Cuando la palabra clave gpgcheck se establece en true en el módulo
ansible.builtin.yum_repository, también debe instalar la clave GPG en el
host gestionado. El módulo ansible.builtin.rpm_key del siguiente ejemplo
implementa la clave pública GPG alojada en un servidor web remoto en el host gestionado
servera.lab.example.com.
---
- name: Configure the company YUM/DNF repositories
  hosts: servera.lab.example.com
  tasks:
    - name: Deploy the GPG public key
      ansible.builtin.rpm_key:
        key: http://materials.example.com/yum/repository/RPM-GPG-KEY-example
        state: present
    - name: Ensure Example Repo exists

Ejercicio Guiado
Administración de software y
suscripciones
Configurar un nuevo repositorio Yum y, desde allí, instala paquetes en sus hosts gestionados.
Resultados
• Configurar un repositorio Yum con el módulo ansible.builtin.yum_repository.
• Administrar las claves GPG de RPM con el módulo ansible.builtin.rpm_key.
• Obtener información sobre los paquetes instalados en un host con el módulo
ansible.builtin.package_facts.
Antes De Comenzar
Con el usuario student en la máquina workstation, use el comando lab para preparar su
sistema para este ejercicio.
Este comando prepara su entorno y garantiza que estén disponibles todos los recursos
requeridos.
[student@workstation ~]$ lab start system-software
Instrucciones
Su organización requiere que el paquete RPM simple-agent esté instalado en todos los hosts.
Este paquete lo proporciona un repositorio Yum interno que mantiene su organización para alojar
paquetes de software desarrollados internamente.
Debe escribir un playbook para asegurarse de que el paquete simple-agent esté instalado
en todos los hosts gestionados. El playbook también debe garantizar que todos los hosts
gestionados estén configurados para usar el repositorio Yum interno.
El repositorio se encuentra en http://materials.example.com/yum/repository. Todos
los paquetes RPM en el repositorio están firmados con un par de claves GPG. La clave pública de
GPG para los paquetes del repositorio está disponible en http://materials.example.com/
yum/repository/RPM-GPG-KEY-example.
 1.
Cambie al directorio /home/student/system-software.
[student@workstation ~]$ cd ~/system-software
[student@workstation system-software]$
 2.
Empiece a escribir el playbook repo_playbook.yml. Defina un solo play en el playbook
que se dirige a todos los hosts. Agregue una cláusula vars al play que defina una sola
variable, custom_pkg, con el valor simple-agent (el nombre del paquete RPM que debe
instalarse en todas partes). Agregue una cláusula tasks vacía al play.

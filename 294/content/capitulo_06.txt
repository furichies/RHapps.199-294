Selección de hosts con patrones de hosts
Objetivos
• Escribir patrones de host sofisticados para seleccionar hosts de manera eficiente para un play.
Referencias a hosts de inventario
Los patrones de host se usan para especificar los hosts en los que se ejecuta su play. En su forma
más simple, el nombre de un host gestionado o un grupo de hosts en el inventario es un patrón de
hosts que especifica ese host o grupo de hosts.
Ya ha usado patrones de hosts en este curso. En un play, la directiva hosts especifica los hosts
gestionados respecto de los cuales se ejecutará el play.
En general, es más fácil controlar a qué hosts apunta un play usando cuidadosamente patrones de
hosts y teniendo grupos de inventario correctos en lugar de establecer condicionales complejos
en las tareas del play. Por lo tanto, es importante tener una comprensión sólida de los patrones de
host.
El siguiente ejemplo de inventario se usa en esta sección para ilustrar patrones de hosts.
[student@controlnode ~]$ cat myinventory
web.example.com
data.example.com
[lab]
labhost1.example.com
labhost2.example.com
[test]
test1.example.com
test2.example.com
[datacenter1]
labhost1.example.com
test1.example.com
[datacenter2]
labhost2.example.com
test2.example.com
[datacenter:children]
datacenter1
datacenter2
[new]
192.168.2.1
192.168.2.2

Para demostrar cómo se resuelven los patrones de host, los siguientes ejemplos ejecutan el
playbook de Ansible playbook.yml, que contiene un play que se edita para tener diferentes
patrones de host para identificar diferentes subconjuntos de hosts gestionados del anterior
inventario de ejemplo.
Hosts administrados
El patrón de host más básico es el nombre de un solo host gestionado detallado en el inventario.
Esto especifica que el host será el único en el inventario en el que se actuará mediante el comando
ansible-navigator.
Cuando se ejecuta el playbook, la primera tarea Gathering Facts debe ejecutarse en todos los
hosts gestionados que coincidan con el patrón de host. Un error durante esta tarea puede hacer
que el host gestionado se elimine del play.
Solo puede usar una dirección IP en un patrón de host si aparece explícitamente en el inventario.
Si la dirección IP no está en el inventario, no podrá usarla para especificar el host aun si la dirección
IP se resuelve a ese nombre de host en el DNS.
En el siguiente ejemplo, se muestra cómo se puede usar el patrón de host para hacer referencia a
una dirección IP contenida en un inventario.
[student@controlnode ~]$ cat playbook.yml
---
...output omitted...
  hosts: 192.168.2.1
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Test Host Patterns] **************************************************
TASK [Gathering Facts] *****************************************************
ok: [192.168.2.1]
...output omitted...
nota
Un problema al hacer referencia a hosts gestionados por medio de una dirección IP
en el inventario es que puede resultar difícil recordar qué dirección IP corresponde
a qué host para sus plays. Sin embargo, es posible que deba especificar el host por
dirección IP para fines de conexión si el host no tiene un nombre de host que pueda
resolver su entorno de ejecución.
Puede apuntar a un alias en una dirección IP específica en su inventario si establece
la variable de host ansible_host. Por ejemplo, podría tener un host en su
inventario denominado host.example que puede usar para patrones de host,
grupos de inventario y conexiones directas con ese nombre a la dirección IP
192.168.2.1 mediante la creación de un archivo host_vars/host.example
que contenga la siguiente variable de host:
ansible_host: 192.168.2.1

Especificar hosts usando un grupo
Puede usar los nombres de los grupos de hosts de inventario como patrones de hosts. Cuando el
nombre de un grupo se usa como patrón de host, especifica que el play actúa en los hosts que son
miembros del grupo.
[student@controlnode ~]$ cat playbook.yml
---
...output omitted...
  hosts: lab
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Test Host Patterns] **************************************************
TASK [Gathering Facts] *****************************************************
ok: [labhost1.example.com]
ok: [labhost2.example.com]
...output omitted...
Recuerde que hay un grupo especial llamado all que coincide con todos los hosts gestionados en
el inventario.
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: all
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Test Host Patterns] **************************************************
TASK [Gathering Facts] *****************************************************
ok: [labhost2.example.com]
ok: [test2.example.com]
ok: [web.example.com]
ok: [data.example.com]
ok: [labhost1.example.com]
ok: [192.168.2.1]
ok: [test1.example.com]
ok: [192.168.2.2]
También hay un grupo especial llamado ungrouped que incluye todos los hosts gestionados en el
inventario que no son miembros de ningún otro grupo:
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: ungrouped
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml

Coincidencia con varios hosts con comodines
Otro método de lograr lo mismo que con el patrón del host all es usar el carácter comodín
asterisco (*), que coincide con cualquier cadena. Si el patrón de host es solo un asterisco entre
comillas, entonces todos los hosts en el inventario coincidirán.
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: '*'
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Test Host Patterns] **************************************************
TASK [Gathering Facts] *****************************************************
ok: [labhost2.example.com]
ok: [test2.example.com]
ok: [web.example.com]
ok: [data.example.com]
ok: [labhost1.example.com]
ok: [192.168.2.1]
ok: [test1.example.com]
ok: [192.168.2.2]
Importante
Algunos caracteres que se usan en los patrones de host también tienen significado
para la shell. Si usa caracteres comodín o de lista especiales en un playbook de
Ansible, debe colocar su patrón de host entre comillas simples para asegurarse de
que se analice correctamente.
  hosts: '!test1.example.com,development'
El carácter de asterisco también se puede usar para que coincida con cualquier host gestionado o
grupo que contenga una subcadena específica.
Por ejemplo, el siguiente patrón de host comodín coincide con todos los nombres de inventario
que finalizan en .example.com:
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: '*.example.com'
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml

Importante
Los patrones de host comodín coinciden con todos los nombres de inventario,
hosts y grupos de hosts. No distinguen entre nombres que son nombres de DNS,
direcciones IP o grupos, lo que puede generar ciertas coincidencias inesperadas.
Por ejemplo, compare los resultados de especificar el patrón de host datacenter*
del ejemplo anterior con los resultados del patrón de host data* basado en el
inventario de ejemplo:
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: 'data*'
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Test Host Patterns] **************************************************
TASK [Gathering Facts] *****************************************************
ok: [labhost1.example.com]
ok: [test1.example.com]
ok: [labhost2.example.com]
ok: [test2.example.com]
ok: [data.example.com]
Listas
Se puede hacer referencia a varias entradas en un inventario con listas lógicas. Una lista de
patrones de hosts separados por comas coincide con todos los hosts que coinciden con cualquiera
de esos patrones de hosts.
Si usted proporciona una lista de hosts gestionados separados por comas, se apuntará a todos
estos hosts gestionados:
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: labhost1.example.com,test2.example.com,192.168.2.2
...output omitted...
[student@controlnode ~]$ ansible-navigator run \
> -m stdout playbook.yml
PLAY [Test Host Patterns] **************************************************
TASK [Gathering Facts] *****************************************************
ok: [labhost1.example.com]
ok: [test2.example.com]
ok: [192.168.2.2]

[student@controlnode ~]$ cat playbook.yml

nota
El carácter de dos puntos (:) puede usarse en lugar de una coma. Sin embargo, la
coma es el separador preferido, en especial, cuando se trabaja con direcciones IPv6
como nombres de hosts gestionados. Puede ver la sintaxis de los dos puntos en
ejemplos anteriores.
Si un ítem en una lista comienza con un carácter &, los hosts deben coincidir con ese ítem para
coincidir con el patrón de host. Funciona de manera similar que un AND lógico.
Por ejemplo, en nuestro ejemplo de inventario, el siguiente patrón de host coincidirá con las
máquinas en el grupo lab solo si también se encuentran en el grupo datacenter1:
[student@controlnode ~]$ cat playbook.yml
...output omitted...
  hosts: lab,&datacenter1
...output omitted...

capítulo 6 |  Administración de plays y playbooks complejos
Inclusión e importación de archivos
Objetivos
• Administrar playbooks grandes importando o incluyendo otros playbooks o tareas desde
archivos externos, ya sea sin condiciones o sobre la base de una prueba condicional.
Gestión de playbooks grandes
Cuando un playbook se torna largo o complejo, puede dividirlo en archivos más pequeños para
que sea más fácil de administrar. Puede combinar varios playbooks en un playbook principal o
insertar listas de tareas de un archivo a un play. Esto puede facilitar la reutilización de plays o
secuencias de tareas en diferentes proyectos.
Inclusión o importación de archivos
Ansible soporta dos operaciones para incorporar contenido en un playbook. Usted puede incluir
contenido, o puede importar contenido.
Cuando incluye contenido, es una operación dinámica. Los procesos de Ansible incluyeron
contenido durante la ejecución del playbook, a medida que se abordaba el contenido.
Cuando importa contenido, es una operación estática. Los preprocesos de Ansible importaron
contenido cuando se analizó inicialmente el playbook, antes de que comience la ejecución.
Importación de playbooks
Use el módulo ansible.builtin.import_playbook para importar archivos externos que
contienen listas de plays en un playbook. En otras palabras, puede tener un playbook principal que
importa uno o más playbooks adicionales.
Debido a que el contenido que se importa es un playbook completo, el módulo
ansible.builtin.import_playbook solo se puede usar en el nivel superior de un playbook
y no se puede usar dentro de un play. Si importa varios playbooks, se importarán y ejecutarán en
orden.
A continuación, se muestra un ejemplo simple de un playbook principal que importa dos playbooks
adicionales:
- name: Prepare the web server
  ansible.builtin.import_playbook: web.yml
- name: Prepare the database server
  ansible.builtin.import_playbook: db.yml
También puede intercalar plays en su playbook principal con playbooks importados.

Inclusión de archivos de tareas
También puede incluir de forma dinámica un archivo de tarea en un play dentro de un playbook
usando el módulo ansible.builtin.include_tasks.
---
- name: Install web server

El módulo ansible.builtin.include_tasks no procesa el contenido en el playbook hasta
que se ejecuta el play y se alcanza esa parte de este. El orden en el que se procesa el contenido
del playbook afecta el funcionamiento del módulo ansible.builtin.include_tasks.
• Al usar el módulo ansible.builtin.include_tasks, las declaraciones condicionales, como
when, establecidas en la inclusión determinan si las tareas están incluidas en el play.
• Si ejecuta ansible-navigator run --list-tasks para enumerar las tareas
del playbook, no se muestran las tareas en los archivos de tareas incluidos. Se
muestran las tareas que incluyen los archivos de tareas. En comparación, el módulo
ansible.builtin.import_tasks no enumera las tareas que importan archivos de tareas,
sino las tareas individuales de los archivos de tareas importados.
• No puede usar ansible-navigator run --start-at-task para iniciar la ejecución del
playbook desde una tarea que se encuentra en un archivo de tareas incluido.
• No puede usar una declaración notify para desencadenar un nombre de controlador que se
encuentra en un archivo de tarea incluido. Puede desencadenar un controlador en el playbook
principal que incluye un archivo de tareas completo, en cuyo caso se ejecutarán todas las tareas
en el archivo incluido.
Importación e inclusión con condicionales
Las declaraciones condicionales se comportan de manera diferente dependiendo de si está
importando o incluyendo tareas.
• Cuando agrega un condicional a una tarea que usa un módulo ansible.builtin.import_*,
Ansible aplica la condición a todas las tareas dentro del archivo importado.
• Cuando usa un condicional en una tarea que usa un módulo ansible.builtin.include_*,
la condición se aplica solo a la tarea de inclusión en sí y no a ninguna otra tarea dentro del
archivo incluido.
En otras palabras, si coloca un condicional en una tarea que importa contenido, cada tarea en el
contenido importado realiza esa verificación condicional antes de ejecutarse.
Sin embargo, si coloca un condicional en una tarea que incluye contenido, entonces el condicional
determina si la inclusión ocurre o no. Si ocurre la inclusión, todas las tareas incluidas se ejecutan
normalmente.

Importante
Las versiones anteriores de Ansible usaban el módulo
ansible.builtin.include para incluir playbooks y archivos de tareas, según el
contexto. Esta función está en desuso por varios motivos.
Antes de Ansible 2.0, el módulo ansible.builtin.include funcionaba
como una importación estática. En Ansible 2.0, se cambió para que funcione
dinámicamente, pero esto causó ciertas limitaciones. En Ansible 2.1, se hizo posible
que el módulo ansible.builtin.include sea dinámico o estático dependiendo
de la configuración de la tarea, lo que era confuso y causaba errores. También hubo
problemas para garantizar que el módulo ansible.builtin.include funcionase
correctamente en todos los contextos.
Por lo tanto, ansible.builtin.include se reemplazó en Ansible 2.4 con
nuevas directivas como ansible.builtin.include_tasks, import_tasks y
ansible.builtin.import_playbook. Podría encontrar ejemplos del módulo
ansible.builtin.include en playbooks anteriores, pero debe evitar usarlo en
otros más nuevos.

Resumen
• Los patrones de host se usan para especificar los hosts gestionados a los que deben apuntar los
plays.
• Puede especificar una lista de múltiples patrones de host en la directiva hosts de un play.
• Puede usar la característica import_playbook para incorporar archivos de play externos a los
playbooks.
• Puede usar la característica include_tasks o import_tasks para incorporar archivos de
tareas externos a los playbooks.
• Cuando incluye contenido, Ansible lo procesa dinámicamente a medida que se alcanza el
contenido. Cuando importa contenido, Ansible lo preprocesa antes de que comience la
ejecución.
